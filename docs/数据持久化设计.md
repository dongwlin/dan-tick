## 2. 实体职责与关系

```text
rooms 1 ─── N tasks 1 ─── N task_messages
              │
              └────── N executions 1 ─── N send_attempts

app_settings                （非敏感应用配置）
系统 Keyring                （独立于 SQLite 的登录凭证）
```

| 实体 | 职责 |
| --- | --- |
| `rooms` | 直播间身份、展示元数据和用户备注 |
| `tasks` | 任务配置、计划定义、启用状态和待处理计划游标 |
| `task_messages` | 当前消息队列及发送顺序 |
| `executions` | 一次计划执行、手动执行、错过的计划实例或独立测试发送 |
| `send_attempts` | HTTP 发送尝试及当时内容快照 |
| `app_settings` | 普通应用配置，具体键与解析规则由设置模块维护 |

每个任务只有一套计划，计划定义和游标直接保存在任务中，无需独立 `schedules` 表。执行记录与发送尝试分开保存，使一次任务运行和每次外部请求都有独立的结果；排队通过执行状态表示，不另建持久化队列表。

数据库承担稳定的结构、关联和唯一性约束；任务类型对应的消息条数等跨行校验由 Go 保存事务处理，复杂业务校验与日历计算也由 Go 完成，不用行级 `CHECK` 代替这些规则。

内部主键与 B 站房间标识各有用途，不能混用。消息按 `position, id` 稳定排序，允许位置值重复，避免重排过程中产生临时唯一约束冲突。

任务配置与历史快照分别维护：任务改名或删除后，历史仍通过当时的任务名、房间标识和消息内容还原执行情况，无需复制整份任务配置。

独立测试发送没有任务归属，仍使用同一套执行和尝试记录，历史查询与清理无需另建分支存储。登录凭证按 [FR-003](PRD.md#fr-003凭证安全) 隔离在系统 Keyring，不进入业务表或普通设置。

## 3. 计划游标与事务领取

`next_due_at` 表示下一次**待处理**计划时刻。它是持久化游标，Cron 注册可以从它重建；手动执行不推进游标，规则未变的编辑保留游标，禁用时清空，重新启用时计算未来计划。

两项持久化约束解决不同问题：

- `uq_executions_scheduled` 以任务和 UTC 计划时刻识别实例，防止同一计划在完成、失败或错过后被再次登记。
- `uq_executions_active_task` 限制同一任务只有一个 `waiting / queued / running` 实例，包括手动执行。手动冲突返回“任务正在执行”；计划冲突登记为 `missed/task_busy` 并推进游标。测试发送没有任务身份，不占用任务执行名额。

计划领取在同一事务内完成：

1. 使用持久化计划时刻作为执行身份，重新核验任务与直播间有效性、启用状态和游标。
2. 判定迟到与活跃冲突，创建可交接的 `waiting` 实例或带结束时间、原因的 `missed` 实例。
3. 通过条件更新推进游标；回调已失效或实例已登记时，不创建新的可执行实例。
4. 提交成功后才交给执行器，交接再核验执行状态，避免并发接管导致重复发送。

任务保存同样将配置、完整消息列表和游标作为一个事务提交；Cron 同步和 Events 发生在提交后。同步失败应报告并允许从数据库重建，不能把已提交的数据描述为回滚。

事务保持短小，HTTP、发送许可等待和 Cron 操作不进入事务。内存锁或单连接池不能替代数据库唯一约束。连接的即时写事务配置及其防止过期 WAL 快照升级写锁的原因见 [数据库连接实现](../internal/storage/storage.go)；并发领取由 [领取测试](../internal/scheduler/claim_test.go) 验证。

自动调度总开关与单个任务启用状态独立。暂停保留任务游标，恢复时先处理过期计划；已经交给执行器的实例不会因暂停自动调度而停止。协调入口与验证见 [调度设置测试](../internal/scheduler/settings_test.go)。

## 4. 执行记录与发送尝试

`waiting` 表示已登记、待交给执行器，`queued` 表示等待账号发送能力，`running` 表示开始执行。其余状态为终态，`missed` 仅用于计划执行；终态写入结束时间，历史按创建时间排序，使尚未实际开始的执行也有稳定位置。

每次 HTTP 请求之前先提交 `pending` 尝试。收到明确响应后记录 `accepted` 或 `failed`，无法判定则记录 `unknown`；尝试结果与执行计数在同一事务内更新，避免结果已保存而汇总未更新。接口接受与实际可见性的区别见 [FR-021](PRD.md#fr-021发送结果处理)。

执行历史中的错误使用安全类别和脱敏说明，落盘前净化，禁止保存 Cookie、完整请求头或原始敏感错误。

`sequence` 标识一次执行内的请求尝试，`message_no` 标识逻辑消息。当前发送链路没有自动 HTTP 重试，两者一致，失败或未知结果结束执行；结果不确定时的产品规则见 [FR-022](PRD.md#fr-022发送超时与重试)。保留两个标识使恢复汇总能按逻辑消息核对，避免同一消息重复计数：

- `sent_count` 统计确认被接口接受的逻辑消息。
- `failed_count` 统计未确认成功的逻辑消息，包括拒绝、未发送和未知结果。
- 恢复时按 `message_no` 去重，已接受的逻辑消息不会同时计为失败。

手动执行保留任务归属但不占用计划身份；测试发送的任务与计划时刻均为空，名称快照为“测试发送”。两者使用同一发送器和历史记录，限流行为见 [FR-019](PRD.md#fr-019任务冲突处理)。

请求前落盘、计数更新和测试发送边界分别由 [手动执行测试](../internal/executor/manual_test.go)、[循环执行测试](../internal/executor/loop_test.go) 与 [测试发送测试](../internal/executor/test_send_test.go) 验证。

## 5. 删除与历史清理

用户删除任务或直播间时采用逻辑删除，禁用相关任务并清空未来游标，保留历史引用的实体。存在活跃执行时拒绝删除，应先停止；禁用任务只影响未来调度，不自动停止当前执行。

重新添加相同 B 站房间时恢复原记录，保留本地身份及历史关联；未填写新备注时保留原备注，不恢复此前已删除的任务。相关事务和恢复行为见 [直播间测试](../internal/room/service_test.go) 与 [任务变更测试](../internal/task/changes_test.go)。

外键限制保护历史引用的任务与直播间；最终物理删除执行记录时，级联清理其发送尝试。确需物理清理已逻辑删除的任务或直播间时，先确认没有历史引用，再按子到父的顺序处理。

历史保留期限由 [PRD 6.4](PRD.md#64-执行历史与诊断日志) 定义。清理仅删除结束时间严格早于截止点的终态执行，不触碰任务配置、调度游标或 Keyring；活跃实例及缺少结束时间的异常终态保留。诊断日志独立清理，不能混作执行历史。实现与边界测试见 [历史清理](../internal/history/cleanup.go) 和 [清理测试](../internal/history/cleanup_test.go)。

## 6. 时间表示与恢复

本地日期、时间和星期描述日历规则，必须结合任务的 IANA 时区解释；计划身份、游标及执行时刻采用 UTC Unix 毫秒，避免系统时区变化或夏令时导致身份不稳定。具体编码以业务模型和迁移为准，不对所有时间字段预设统一的空值约定。

周期日历由 [schedule](../internal/schedule/schedule.go) 计算，Cron 只按持久化游标注册一次性唤醒，避免两套日历计算产生分歧。夏令时中不存在的本地时间跳过该天，重复时间只取第一次真实时刻；相应行为见 [日历测试](../internal/schedule/schedule_test.go)。

实时 Cron 回调允许 **30 秒**迟到宽限，含边界；超过时登记 `missed/schedule_overdue` 并推进未来游标。显式启动或唤醒恢复不补发已到期实例，即使迟到不足 30 秒。判定与边界测试由 [恢复实现](../internal/scheduler/recovery.go) 和 [恢复测试](../internal/scheduler/recovery_test.go) 维护。

启动时先原子处理遗留的 `waiting / queued / running` 实例，将其标为 `interrupted`；未决 `pending` 尝试改为 `unknown` 并核对计数，再恢复未来调度。事务已提交但尚未交给执行器的实例也按中断处理，不能自动重放不确定的外部请求。

唤醒恢复仅处理过期计划游标，不中断本进程仍在执行的实例。

长期离线的周期任务只为当前过期游标保留一条代表性错过记录，再推进下一未来时刻；一次性任务以 `missed` 结束并清空游标。系统时间倒拨不使持久化游标后退，编辑计划不创建过去的计划实例。产品恢复要求见 [PRD 第 7 节](PRD.md#7-调度与运行可靠性)。

## 7. 迁移与升级

迁移文件存放在 [internal/storage/migrations](../internal/storage/migrations/)，通过 `go:embed` 内嵌，由 Bun 管理版本记录。事务型迁移使用 `.tx.up.sql` 与 `--bun:split`，不在运行时自动同步 Model 来代替版本化迁移。

数据库打开时配置连接并验证外键，迁移成功后才进行恢复和调度。连接参数以 [storage.go](../internal/storage/storage.go) 为准，初始化及关闭顺序见 [后端生命周期约定](../internal/AGENTS.md#4-应用与后台生命周期)。失败时报告并停止依赖数据库的启动，不自动删除、重建或覆盖用户数据库。

已发布迁移保持不变，结构变化追加新迁移。不兼容改动采用事务内表重建并验证数据与外键；[测试发送历史迁移](../internal/storage/migrations/20261013000100_test_send_history.tx.up.sql) 是放宽任务归属约束并保留旧数据的实例。

升级前备份必须保证 SQLite 快照一致性，不能直接复制仍在写入的 WAL 主文件。升级失败停止启动，不自动降级或覆盖用户文件。回滚 SQL 服务于开发和迁移验证，可能删除新版本数据，正式界面不提供“回滚并清空数据”操作。

空库初始化、重复迁移、重新打开后的约束、旧数据升级保留、迁移失败回滚及损坏数据库保护由 [storage_test.go](../internal/storage/storage_test.go) 验证；测试方法遵循 [后端验证约定](../internal/AGENTS.md#5-go-验证)。
