# 构建与发布

本项目的桌面流水线见 [Desktop Build](../.github/workflows/desktop-build.yml)，目标为 Linux amd64 AppImage、Windows amd64 EXE 和用户级 NSIS 安装包。构建与打包成功不代表实机验收通过；首个正式版本仍须满足 [开发计划 G3](开发计划.md) 和 [PRD 验收标准](PRD.md#11-第一版验收标准)。

## CI 产物与 Release

- Push、Pull Request 和手动运行都会构建两平台，并将产物上传为 Actions artifacts，保留 14 天。Linux 使用一个下载入口；Windows 的独立 EXE 和 NSIS 安装器分别提供下载入口。各 Windows 入口包含对应的 `.sha256` 校验文件；安装器入口还包含 Windows 汇总清单，下载两个入口并解压到同一目录即可运行汇总校验。手动运行无需输入版本。
- 只有 **Push 正式版本 Tag** 才发布 GitHub Release。正式 Tag 必须完整匹配 `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`，例如 `v0.0.1`；`test-*`、`v0.0.1-beta.1` 等 Tag 不发布 Release，也不作为历史版本基线。
- 在分支上构建，即使 HEAD 已有正式 Tag，也只上传 CI 产物；手动选择 Tag 运行同样不发布 Release。
- Release 复用当前流水线的 CI 产物，不重新编译。Linux / Windows 构建和质量检查、Linux AppImage 跨发行版启动检查全部通过，且三类文件及 SHA-256 校验全部通过后，才将草稿发布。
- 上传失败会留下草稿，重跑相同 Tag 的工作流可以继续。已发布的 Release 不自动覆盖；修复应使用新的版本 Tag。

产物名称示例：

```text
dan-tick-v0.0.1-linux-amd64.AppImage
dan-tick-v0.0.1-windows-amd64.exe
dan-tick-v0.0.1-windows-amd64-installer.exe
SHA256SUMS-linux-amd64.txt
SHA256SUMS-windows-amd64.txt
```

从 Actions 页面下载的 ZIP 不保留 Linux 可执行位。解压后使用 `chmod +x dan-tick-*.AppImage`，再运行 AppImage；可使用 `sha256sum --check SHA256SUMS-linux-amd64.txt` 核验下载文件。Windows 独立 EXE 仍需要系统具备 WebView2 Runtime；NSIS 安装包包含在线引导安装器，缺少 Runtime 时需要联网安装。

流水线使用 Ubuntu 24.04 和 Windows Server 2022 原生 runner，固定项目的 Go、Node.js、pnpm 和 Wails CLI 版本。Ubuntu 24.04 是 Linux 发布构建基线；在较新系统本地编译的 AppImage 不自动获得同样的兼容范围。当前产物没有代码签名，CI 不需要个人账号凭证或发布用 PAT，Release job 使用具有 `contents: write` 权限的 `GITHUB_TOKEN`。

## Linux AppImage 运行依赖与兼容范围

AppImage 封装应用可执行文件、桌面入口、图标和 AppRun，使用目标发行版的 **GTK4 4.14 或更新版本、WebKitGTK 6.0**。首次运行前，按发行版安装运行依赖：

```sh
# Ubuntu 24.04 / 26.04、Debian 13
sudo apt install libgtk-4-1 libwebkitgtk-6.0-4

# Fedora 44
sudo dnf install gtk4 webkitgtk6.0
```

AppRun 启动前用 `ldd -r` 检查缺失的动态库和符号，失败时在终端给出中文说明和对应的 `apt` / `dnf` 安装命令；桌面会话有 `zenity` 时同时显示对话框。软件源中的包及其依赖负责提供配套的 WebKit helper、沙箱工具和图形运行时。账号凭证仍需要可解锁的 Secret Service，例如 GNOME Keyring，或启用 Secret Service 接口的 KWallet；安全存储缺失、锁定或不可用时应用会明确失败，不回退明文。

| 发行版 | CI 检查版本 | 兼容策略 |
| --- | --- | --- |
| Ubuntu | 24.04、26.04 | 24.04 为发布构建基线，同时检查较新版本 |
| Debian | 13 | 使用发行版提供的 GTK4 / WebKitGTK 6.0 |
| Fedora | 44 | 使用发行版提供的 GTK4 / WebKitGTK 6.0 |

优先适配三个发行版的较新稳定版本；旧版本仅尽力兼容，低于 Ubuntu 24.04 的构建基线或没有上述运行依赖时不作运行保证。AppImage 是分发格式，兼容性仍取决于构建基线、运行依赖和目标系统测试，见 [AppImage 官方兼容性建议](https://docs.appimage.org/reference/best-practices.html)。

打包使用固定的 `appimagetool 1.9.1` 和 [AppImage type-2 runtime](https://github.com/AppImage/type2-runtime) 的 `20251108` 发布版本，两者均核验 SHA-256。静态链接的 runtime 让目标系统无需安装 `libfuse2`。正常挂载仍需要内核 FUSE 和可用的 `/dev/fuse`；容器或受限环境中可使用提取运行方式：

```sh
./dan-tick-v0.0.1-linux-amd64.AppImage --appimage-extract-and-run
```

提取运行同样需要 GTK4 / WebKitGTK 6.0。AppRun 保留系统选择的 X11 / Wayland 后端和 WebKit 沙箱，使用发行版成套运行时，避免 Ubuntu 与 Fedora 的 helper 路径、图形库和 WebKit 版本混用。

CI 将 Ubuntu 24.04 构建的**同一个最终 AppImage**放入上述四个测试环境，通过隔离的 D-Bus 会话、Xvfb 与 AT-SPI 核对真实 Vue 页面加载、WebKit helper 和应用持续运行；提取运行路径也包含最终 AppImage runtime 与 AppRun。该检查不访问真实 B 站接口或用户数据，其结果和诊断截图由对应 workflow 记录，失败会阻止 Release。容器的 X11 / 软件渲染检查不能替代正常桌面的 Wayland、GPU、托盘、窗口和 Keyring 人工验收，也不代表 G1～G3 已通过。

2026-10-13 本地验证：用新打包链重新封装 `5210514a` 的 Ubuntu CI 二进制，同一个包在上述四个容器中均通过页面加载检查；当前源码重新构建的包额外在 Ubuntu 26.04 / Fedora 44 通过，WebKit helper 的 seccomp 与 no-new-privileges 标志均已核对。Fedora 44 宿主上的 FUSE 挂载及包内执行权限检查通过。测试均使用临时用户数据；容器无网络，未验证扫码、发送或 Keyring。

如果以后要求目标系统无需预装 GTK / WebKit，可评估 [Flatpak 的跨发行版 runtime](https://docs.flatpak.org/en/latest/basic-concepts.html#runtimes)。Flatpak 还需要核对 Secret Service、文件与目录访问、托盘和自启动等桌面权限；它是后续候选方案，当前只交付上述 AppImage。

## 自动版本

[构建工具](../build/tools/) 从实际检出的 Git HEAD 计算版本，CI 完整获取历史和 Tags。Pull Request 默认构建 GitHub 的合并提交，版本中的 Commit 对应这个实际 HEAD。

| 场景 | 显示版本 | 数字打包版本 |
| --- | --- | --- |
| 本地构建 / 开发 | `dev` | `build/config.yml` 的 `info.version` |
| 正式 Tag Push | Tag 原名，如 `v0.0.1` | 去掉 `v`，如 `0.0.1` |
| CI，存在祖先正式 Tag | 最近正式 Tag + 8 位 HEAD，如 `v0.0.1-a1b2c3d4` | 该正式 Tag 的数字版本 |
| CI，无祖先正式 Tag | `dev-a1b2c3d4` | 配置的数字兜底版本 |

数字打包版本用于 Windows 固定资源版本（四段，如 `0.0.1.0`）；界面、诊断信息、Windows 字符串资源和产物名称使用完整显示版本。不能把 `dev`、带 `v` 的 Tag 或 Commit 后缀直接放进 Windows 数值资源。

每次实际编译桌面可执行文件前记录 UTC RFC 3339 构建时间，通过 Go `-ldflags -X` 注入版本、时间和 Commit；原生与 Docker 构建使用同一组定义。应用通过 `ApplicationService.GetBuildInfo` 获取只读信息，界面按本地时区显示日期。获取不到 Git 信息时保留缺省值，不使用启动时间或文件时间替代。

流水线在版本 Job 中生成 `DAN_TICK_VERSION`、`DAN_TICK_PACKAGE_VERSION`、`DAN_TICK_COMMIT`，统一传给各平台。日常本地开发不需要设置这些变量，不会因为附近存在正式 Tag 就显示正式版本。

## 配置与本地打包

[build/config.yml](../build/config.yml) 的 `info` 是公司、产品名称、产品标识、描述、版权和注释的配置入口。普通目标平台构建会自动刷新对应资源：Windows EXE / NSIS 使用同步后的资源；Linux AppImage 使用实际的 `build/linux/dan-tick.desktop`。CI 版本由 Git 自动覆盖，**发布时不必修改 `info.version`**。文件顶层的 `version: '3'` 是 Wails 配置格式版本。

在仓库根目录执行：

```sh
# 当前平台生产构建，自动生成 Binding 和前端产物
wails3 build

# Windows EXE + 用户级 NSIS
wails3 task package GOOS=windows ARCH=amd64 INSTALL_SCOPE=user

# Linux 仅 AppImage（通用 package 还会生成 DEB / RPM / Arch 包）
wails3 task linux:create:appimage ARCH=amd64

# 检查当前版本判定，无需修改配置
go run ./build/tools version
```

Windows NSIS 默认用户级安装：安装目录为 `%LOCALAPPDATA%\Programs\Dan Tick`，注册项写入 HKCU，快捷方式属于当前用户。显式使用 `INSTALL_SCOPE=machine` 才构建机器级安装器。

原始产物在 `bin/`，流水线将其复制、按版本重命名并生成校验文件后上传。本地需安装 NSIS 的 `makensis`；Linux 编译需 C 编译器及 GTK4 / WebKitGTK 6.0 开发包，AppImage 打包脚本会获取固定版本的 `appimagetool`。`build/linux/appimage/build.sh` 直接组装 AppDir，不调用 Wails AppImage generator 或 linuxdeploy，也不复制 GTK / WebKit 动态库或 helper、修改 WebKit 二进制路径、关闭沙箱。AppImage 打包应在目标架构的 Linux 环境中完成，跨架构编译二进制成功不代表可以在宿主机打包 AppImage。

`common:update:build-assets` 已改为支持平台的资源同步任务，可传 `PLATFORM=linux` 或 `PLATFORM=windows`，默认同步两者。它只更新当前目标需要的资源，保留 nFPM 等未参与本次发布的定制。直接使用 Wails 原生 `wails3 update build-assets` 仍会覆盖多个平台的模板资源，升级模板时须检查生成差异。

完成 G3 后，在准备发布的提交上创建并推送正式 Tag 即可触发发布，例如首发 `v0.0.1`。Tag 必须先存在于远端；流水线不会自动创建或移动 Tag。
