# 构建与发布

本项目的桌面流水线见 [Desktop Build](../.github/workflows/desktop-build.yml)，目标为 Linux amd64 AppImage、Windows amd64 EXE 和用户级 NSIS 安装包。构建与打包成功不代表实机验收通过；首个正式版本仍须满足 [开发计划 G3](开发计划.md) 和 [PRD 验收标准](PRD.md#11-第一版验收标准)。

## CI 产物与 Release

- Push、Pull Request 和手动运行都会构建两平台，并将产物上传为 Actions artifacts，保留 14 天。Linux 使用一个下载入口；Windows 的独立 EXE 和 NSIS 安装器分别提供下载入口。各 Windows 入口包含对应的 `.sha256` 校验文件；安装器入口还包含 Windows 汇总清单，下载两个入口并解压到同一目录即可运行汇总校验。手动运行无需输入版本。
- 只有 **Push 正式版本 Tag** 才发布 GitHub Release。正式 Tag 必须完整匹配 `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`，例如 `v0.0.1`；`test-*`、`v0.0.1-beta.1` 等 Tag 不发布 Release，也不作为历史版本基线。
- 在分支上构建，即使 HEAD 已有正式 Tag，也只上传 CI 产物；手动选择 Tag 运行同样不发布 Release。
- Release 复用当前流水线的 CI 产物，不重新编译。Linux / Windows 构建和质量检查、Linux AppImage 跨发行版启动检查全部通过，且三类文件及 SHA-256 校验全部通过后，才将草稿发布。
- 上传失败会留下草稿，重跑相同 Tag 的工作流可以继续。已发布的 Release 不自动覆盖；修复应使用新的版本 Tag。

产物名称示例：

```text
dan-tick-v0.0.1-linux-amd64.AppImage
dan-tick-v0.0.1-windows-amd64.exe
dan-tick-v0.0.1-windows-amd64-installer.exe
SHA256SUMS-linux-amd64.txt
SHA256SUMS-windows-amd64.txt
```

从 Actions 页面下载的 ZIP 不保留 Linux 可执行位。解压后使用 `chmod +x dan-tick-*.AppImage`，再运行 AppImage；可使用 `sha256sum --check SHA256SUMS-linux-amd64.txt` 核验下载文件。Windows 独立 EXE 仍需要系统具备 WebView2 Runtime；NSIS 安装包包含在线引导安装器，缺少 Runtime 时需要联网安装。

流水线使用 Ubuntu 24.04 和 Windows Server 2022 原生 runner，固定项目的 Go、Node.js、pnpm 和 Wails CLI 版本。Ubuntu 24.04 是 Linux 发布构建基线；在较新系统本地编译的 AppImage 不自动获得同样的兼容范围。当前产物没有代码签名，CI 不需要个人账号凭证或发布用 PAT，Release job 使用具有 `contents: write` 权限的 `GITHUB_TOKEN`。

## Linux AppImage 自带运行时与兼容范围

AppImage **自带**应用运行所需的 GUI 与 Web 运行时：GTK4、WebKitGTK 6.0、JavaScriptCore、WebKit helper、注入库、GIO 模块（含 TLS）、gdk-pixbuf 加载器、GLib schemas、bwrap / xdg-dbus-proxy 以及它们的动态依赖。用户**不需要**安装 `libgtk-4-1` / `libwebkitgtk-6.0-4`（Ubuntu、Debian）或 `gtk4` / `webkitgtk6.0`（Fedora），也不需要发行版提供 WebKit helper。

宿主需要提供的内容，以及为什么它们不随包分发：

| 组件 | 策略 |
| --- | --- |
| glibc ≥ 2.39、libstdc++、libgcc | 必须与运行内核和宿主 NSS / 图形驱动一致；包内其余库都由同一次构建产出 |
| 字体与 fontconfig 配置 | 使用宿主字体；包内只带 fontconfig 运行库 |
| 显卡驱动栈 | 包内提供 libGL / libEGL / libgbm / libdrm / libvulkan 加载器，具体驱动仍来自宿主 |
| X11 / Wayland 会话 | 由 GTK 按宿主环境选择后端，AppRun 不强制 `GDK_BACKEND` |
| 内核用户命名空间与安全策略 | WebKit 沙箱需要用户命名空间；Ubuntu 的用户命名空间限制是宿主策略，见下 |

| 发行版 | CI 检查版本 | 状态 |
| --- | --- | --- |
| Ubuntu | 26.04 | 验收目标 |
| Debian | 13 | 验收目标 |
| Fedora | 44 | 验收目标 |
| Ubuntu | 24.04 | 构建基线；仅尽力兼容，不纳入验收矩阵 |

包内的 WebKit 是项目自己编译的 WebKitGTK（版本、源码校验与构建选项见 [build/linux/runtime](../build/linux/runtime/README.md)），并应用 `relocatable-runtime.patch`：helper 目录、注入库目录、数据目录与沙箱绑定目录都从**实际加载到的 WebKit 库位置**推导。发行版 release WebKit 不会读取 `WEBKIT_EXEC_PATH`（该分支只在 `ENABLE(DEVELOPER_MODE)` 下编译），因此不采用只设置环境变量的方案；也不做无差别替换 `/usr` 字符串或只恢复权限的“修复”。沙箱保持启用：bwrap 与 xdg-dbus-proxy 优先使用系统路径（Ubuntu 把用户命名空间策略绑定在 `/usr/bin/bwrap` 上），系统缺失时使用包内副本，不关闭沙箱、不设置 setuid、不修改用户全局 sysctl。

打包使用固定的 `appimagetool 1.9.1` 与 [AppImage type-2 runtime](https://github.com/AppImage/type2-runtime) 的 `20251108` 版本，两者均核验 SHA-256。静态链接的 runtime 让目标系统无需安装 `libfuse2`；正常挂载仍需要内核 FUSE 与可用的 `/dev/fuse`，容器或受限环境中可使用提取运行方式：

```sh
./dan-tick-v0.0.1-linux-amd64.AppImage --appimage-extract-and-run
```

AppRun 先核对包内 helper、注入库与沙箱程序是否完整，再用 `ldd -r` 检查宿主是否满足 glibc / C++ 运行库要求；失败时在终端给出中文说明，桌面会话有 `zenity` 时同时显示对话框。账号凭证仍需要可解锁的 Secret Service（例如 GNOME Keyring，或启用 Secret Service 接口的 KWallet）；安全存储缺失、锁定或不可用时应用会明确失败，不回退明文。

CI 将 Ubuntu 24.04 构建的**同一个最终 AppImage**放入上述三个测试环境，容器内**不安装** GTK4 / WebKitGTK 6.0。检查内容包括：包内 helper 的执行权限、主程序与 helper 的动态库映射（GTK、WebKit、JavaScriptCore、注入库必须来自包内）、WebKit 沙箱的 seccomp、no-new-privileges 与用户命名空间标志、包内 GIO TLS 模块对本地 HTTPS 测试服务的真实握手，以及真实 Vue 页面通过 AT-SPI 暴露的界面文本（包含只有拿到 Go Binding 结果后才渲染的文案）。运行方式覆盖 FUSE 挂载、`--appimage-extract-and-run` 与在含空格路径中提取运行。该检查不访问真实 B 站接口或用户数据，诊断截图与日志由对应 workflow 记录，失败会阻止 Release；Fedora 环境中额外安装发行版 bubblewrap / xdg-dbus-proxy，以覆盖“优先使用系统沙箱工具”的分支。

容器共享宿主内核、使用专用 AppArmor profile、并在 X11 与软件渲染下运行，因此这些检查**不能**代表正常桌面的 Wayland、GPU、托盘、窗口、Keyring、SELinux 或默认 AppArmor 策略验收，也不代表 G1～G3 已通过。Ubuntu 24.04 及更新的 Ubuntu 默认限制未受信任的用户命名空间：GitHub 的 Ubuntu 24.04 runner 会限制未受 AppArmor 配置允许的用户命名空间，因此 smoke job 仅为自己的测试容器加载带 `userns` 权限的专用 profile，启动前用 `bwrap` 核对 UID 映射与 `/proc` 挂载；不修改宿主全局 sysctl，也不要求用户改机器设置。真实桌面上若发行版策略禁止未受信任的用户命名空间（例如 Ubuntu 桌面默认设置），系统 bwrap 的 AppArmor profile 通常已放行；无法放行的环境属于平台限制，需要发行版侧配置，应用不会用关闭沙箱的方式绕过。

无法在 CI 中完成的项目按实机验收处理：Wayland 与 GPU 渲染、托盘与窗口行为、Keyring 解锁、自启动与后台生命周期、以及 Debian / Fedora 上的 SELinux 策略。这些项目未完成前不宣称验收通过。

## 自动版本

[构建工具](../build/tools/) 从实际检出的 Git HEAD 计算版本，CI 完整获取历史和 Tags。Pull Request 默认构建 GitHub 的合并提交，版本中的 Commit 对应这个实际 HEAD。

| 场景 | 显示版本 | 数字打包版本 |
| --- | --- | --- |
| 本地构建 / 开发 | `dev` | `build/config.yml` 的 `info.version` |
| 正式 Tag Push | Tag 原名，如 `v0.0.1` | 去掉 `v`，如 `0.0.1` |
| CI，存在祖先正式 Tag | 最近正式 Tag + 8 位 HEAD，如 `v0.0.1-a1b2c3d4` | 该正式 Tag 的数字版本 |
| CI，无祖先正式 Tag | `dev-a1b2c3d4` | 配置的数字兜底版本 |

数字打包版本用于 Windows 固定资源版本（四段，如 `0.0.1.0`）；界面、诊断信息、Windows 字符串资源和产物名称使用完整显示版本。不能把 `dev`、带 `v` 的 Tag 或 Commit 后缀直接放进 Windows 数值资源。

每次实际编译桌面可执行文件前记录 UTC RFC 3339 构建时间，通过 Go `-ldflags -X` 注入版本、时间和 Commit；原生与 Docker 构建使用同一组定义。应用通过 `ApplicationService.GetBuildInfo` 获取只读信息，界面按本地时区显示日期。获取不到 Git 信息时保留缺省值，不使用启动时间或文件时间替代。

流水线在版本 Job 中生成 `DAN_TICK_VERSION`、`DAN_TICK_PACKAGE_VERSION`、`DAN_TICK_COMMIT`，统一传给各平台。日常本地开发不需要设置这些变量，不会因为附近存在正式 Tag 就显示正式版本。

## 配置与本地打包

[build/config.yml](../build/config.yml) 的 `info` 是公司、产品名称、产品标识、描述、版权和注释的配置入口。普通目标平台构建会自动刷新对应资源：Windows EXE / NSIS 使用同步后的资源；Linux AppImage 使用实际的 `build/linux/dan-tick.desktop`。CI 版本由 Git 自动覆盖，**发布时不必修改 `info.version`**。文件顶层的 `version: '3'` 是 Wails 配置格式版本。

在仓库根目录执行：

```sh
# 当前平台生产构建，自动生成 Binding 和前端产物
wails3 build

# Windows EXE + 用户级 NSIS
wails3 task package GOOS=windows ARCH=amd64 INSTALL_SCOPE=user

# Linux 自包含 AppImage：在固定打包镜像内编译并打包（需要 Docker）
wails3 task linux:create:appimage ARCH=amd64

# 仅在 build/linux/runtime 变更后重建并导出 WebKit 运行时产物（耗时数十分钟）
wails3 task linux:create:webkit-runtime

# 检查当前版本判定，无需修改配置
go run ./build/tools version
```

Windows NSIS 默认用户级安装：安装目录为 `%LOCALAPPDATA%\Programs\Dan Tick`，注册项写入 HKCU，快捷方式属于当前用户。显式使用 `INSTALL_SCOPE=machine` 才构建机器级安装器。

原始产物在 `bin/`，流水线将其复制、按版本重命名并生成校验文件后上传。本地需安装 NSIS 的 `makensis`；Linux AppImage 只需要 Docker、curl 和 git：`build/linux/appimage/package.sh` 会下载并校验固定版本的 WebKit 运行时产物、构建固定打包镜像，然后在其中编译应用并组装 AppDir。这样做的原因是应用二进制必须与包内 GTK / WebKit 来自同一次构建——在更新的宿主上编译（例如 GTK 4.22 上的 Fedora）再配旧版包内运行库会产生符号不匹配。WebKit 运行时产物本身由 `build/linux/runtime/build-webkit-runtime.sh` 生成并作为 Release 资产按 SHA-256 固定；`build/linux/appimage/build.sh` 在镜像内组装 AppDir，不调用 Wails AppImage generator 或 linuxdeploy。AppImage 打包应在目标架构的 Linux 环境中完成，跨架构编译二进制成功不代表可以在宿主机打包 AppImage。

`common:update:build-assets` 已改为支持平台的资源同步任务，可传 `PLATFORM=linux` 或 `PLATFORM=windows`，默认同步两者。它只更新当前目标需要的资源，保留 nFPM 等未参与本次发布的定制。直接使用 Wails 原生 `wails3 update build-assets` 仍会覆盖多个平台的模板资源，升级模板时须检查生成差异。

完成 G3 后，在准备发布的提交上创建并推送正式 Tag 即可触发发布，例如首发 `v0.0.1`。Tag 必须先存在于远端；流水线不会自动创建或移动 Tag。
