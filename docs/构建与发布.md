# 构建与发布

本项目的桌面流水线见 [Desktop Build](../.github/workflows/desktop-build.yml)，目标为 Linux amd64 AppImage、Windows amd64 EXE 和用户级 NSIS 安装包。构建与打包成功不代表实机验收通过；版本发布前仍须满足 [PRD 验收标准](PRD.md#11-第一版验收标准) 及其范围约定。

## CI 产物与 Release

- Push、Pull Request 和手动运行都会构建两平台，并将产物上传为 Actions artifacts，保留 14 天。Linux 使用一个下载入口；Windows 的独立 EXE 和 NSIS 安装器分别提供下载入口。每个产物都随附一个与它同名的 `.sha256` 校验文件，不发布跨文件的汇总清单。手动运行无需输入版本。
- 只有 **Push 正式版本 Tag** 才发布 GitHub Release。正式 Tag 必须完整匹配 `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`，例如 `v0.0.1`；`test-*`、`v0.0.1-beta.1` 等 Tag 不发布 Release，也不作为历史版本基线。
- 在分支上构建，即使 HEAD 已有正式 Tag，也只上传 CI 产物；手动选择 Tag 运行同样不发布 Release。
- Release 复用当前流水线的 CI 产物，不重新编译。Linux / Windows 构建和质量检查、Linux AppImage 跨发行版启动检查全部通过，且三类产物及各自的 SHA-256 校验全部通过后，才将草稿发布。
- 上传失败会留下草稿，重跑相同 Tag 的工作流可以继续。已发布的 Release 不自动覆盖；修复应使用新的版本 Tag。

产物名称示例：

```text
dan-tick-v0.0.1-linux-amd64.AppImage
dan-tick-v0.0.1-linux-amd64.AppImage.sha256
dan-tick-v0.0.1-windows-amd64.exe
dan-tick-v0.0.1-windows-amd64.exe.sha256
dan-tick-v0.0.1-windows-amd64-installer.exe
dan-tick-v0.0.1-windows-amd64-installer.exe.sha256
```

从 Actions 页面下载的 ZIP 不保留 Linux 可执行位。解压后使用 `chmod +x dan-tick-*.AppImage`，再运行 AppImage；校验文件内容形如 `<sha256>  <产物名>`，与产物放在同一目录即可执行 `sha256sum --check dan-tick-v0.0.1-linux-amd64.AppImage.sha256` 核验下载文件，Windows 产物同理。Windows 独立 EXE 仍需要系统具备 WebView2 Runtime；NSIS 安装包包含在线引导安装器，缺少 Runtime 时需要联网安装。

流水线使用 Ubuntu 24.04 和 Windows Server 2022 原生 runner，固定项目的 Go、Node.js、pnpm 和 Wails CLI 版本。Ubuntu 24.04 是 Linux 发布构建基线；在较新系统本地编译的 AppImage 不自动获得同样的兼容范围。当前产物没有代码签名，CI 不需要个人账号凭证或发布用 PAT，Release job 使用具有 `contents: write` 权限的 `GITHUB_TOKEN`。

## Linux AppImage 运行依赖与兼容范围

Linux 采用**薄 AppImage + 系统 WebKit**。包内只包含应用二进制、AppRun、桌面入口和图标；GTK4、WebKitGTK 6.0、JavaScriptCore、WebKit helper、注入库、GIO 模块（含 TLS）、gdk-pixbuf 加载器、GLib schemas、bubblewrap / xdg-dbus-proxy 及其动态依赖全部由发行版系统包提供。系统负责这些组件的版本匹配、安全更新与资源路径，AppImage 不收集动态库或覆盖系统 WebKit 路径。

| 发行版 | 版本 | 状态 |
| --- | --- | --- |
| Ubuntu | 26.04 | 适配与验收目标；CI 启动检查 |
| Debian | 13 | 适配与验收目标；CI 启动检查 |
| Fedora | 44 | 适配与验收目标；CI 启动检查 |
| Ubuntu | 24.04 | 编译基线；仅尽力兼容，不纳入验收矩阵 |
| 其他旧版本 | — | 仅尽力兼容，可能缺少所需 GTK / WebKit API 或动态库符号 |

发布包使用 Ubuntu 24.04 的系统开发包编译。该基线用于控制二进制依赖的最低符号版本，不能让缺失或过旧的系统运行时变得可用；较新系统本地编译的包也不自动获得同样的兼容范围。运行需要正常的 X11 / Wayland 桌面会话、字体、显卡驱动与可用的 WebKit 沙箱环境。

运行前安装系统依赖：

```sh
# Ubuntu 26.04 / Debian 13（Ubuntu 24.04 的包名相同）
sudo apt update
sudo apt install libgtk-4-1 libwebkitgtk-6.0-4 glib-networking ca-certificates

# Fedora 44
sudo dnf install gtk4 webkitgtk6.0 glib-networking ca-certificates
```

包名按发行版官方索引核对：[Ubuntu GTK4](https://packages.ubuntu.com/resolute/amd64/libs/libgtk-4-1)、[Ubuntu WebKitGTK 6.0](https://packages.ubuntu.com/resolute/amd64/libwebkitgtk-6.0-4)、[Debian WebKitGTK 6.0](https://packages.debian.org/trixie/libwebkitgtk-6.0-4)、[Fedora WebKitGTK 6.0](https://packages.fedoraproject.org/pkgs/webkitgtk/webkitgtk6.0/fedora-44.html)。WebKit 包会安装匹配的 JavaScriptCore、helper、注入库及系统沙箱工具；不要混装不同发行版的这些文件。GIO TLS 来自 [Ubuntu glib-networking](https://packages.ubuntu.com/resolute/glib-networking)、[Debian glib-networking](https://packages.debian.org/trixie/glib-networking) 和 [Fedora glib-networking](https://packages.fedoraproject.org/pkgs/glib-networking/glib-networking/)。上述命令是运行依赖，编译应用还需对应 Wails 开发包与 C 编译器。

打包使用固定的 `appimagetool 1.9.1` 与 [AppImage type-2 runtime](https://github.com/AppImage/type2-runtime) 的 `20251108` 版本，两者均核验 SHA-256。这里的 type-2 runtime 负责 AppImage 挂载和启动，与系统 WebKit 运行时独立。静态链接的 type-2 runtime 无需系统安装 `libfuse2`；正常挂载仍需要内核 FUSE、可用的 `/dev/fuse` 与系统 `fusermount` / `fusermount3` helper。系统已有可用 helper 时无需另装，否则安装发行版的 `fuse3` 包（[Ubuntu](https://packages.ubuntu.com/en/resolute/amd64/fuse3)、[Debian](https://packages.debian.org/trixie/fuse3)、[Fedora](https://packages.fedoraproject.org/pkgs/fuse3/fuse3/)）：

```sh
# Ubuntu / Debian
sudo apt install fuse3

# Fedora
sudo dnf install fuse3
```

容器或受限环境中可使用提取运行方式，无需 FUSE 挂载：

```sh
./dan-tick-v0.0.1-linux-amd64.AppImage --appimage-extract-and-run
```

AppRun 使用 `ldd -r` 检查系统动态库，缺少依赖或符号不兼容时在终端提示安装命令；桌面会话有 `zenity` 时同时显示对话框。账号凭证仍需要可解锁的 Secret Service（例如 GNOME Keyring，或启用 Secret Service 接口的 KWallet）；安全存储缺失、锁定或不可用时应用会明确失败，不回退明文。

CI 将 Ubuntu 24.04 构建的**同一个最终 AppImage**放入上述三个目标发行版容器，并安装各自的系统 GTK4 / WebKitGTK 6.0 / GIO TLS 运行时。检查内容包括：AppDir 未捆绑系统运行时、主程序和 helper 的动态库映射及注入库均来自系统、WebKit 沙箱的 seccomp / no-new-privileges / 用户命名空间标志，以及真实 Vue 页面通过 AT-SPI 暴露的界面文本（包含只有拿到 Go Binding 结果后才渲染的文案）。运行方式覆盖 FUSE 挂载、`--appimage-extract-and-run` 与含空格路径中的提取运行。该检查不访问真实 B 站接口或用户数据，诊断截图与日志由对应 workflow 记录，失败会阻止 Release。

容器共享宿主内核、使用专用 AppArmor profile，并在 X11 与软件渲染下运行，因此这些检查**不能**代表正常桌面的 Wayland、GPU、托盘、窗口、Keyring、SELinux 或默认 AppArmor 策略验收，也不代表 G1～G3 已通过。smoke job 仅为自己的测试容器加载带 `userns` 权限的专用 profile，在运行中的 WebKit 进程内检查用户命名空间、seccomp 和 `NoNewPrivs`，不修改宿主全局 sysctl。真实桌面上仍需发行版安全策略允许系统 WebKit 的用户命名空间与沙箱工具运行；不满足的环境属于平台限制，应用不会关闭沙箱、设置 setuid 或修改全局安全设置来绕过。

Wayland 与 GPU 渲染、托盘与窗口行为、Keyring 解锁、自启动与后台生命周期、AppArmor / SELinux 策略按正常桌面人工验收处理。这些项目未完成前不宣称验收通过。

## 自动版本

[构建工具](../build/tools/) 从实际检出的 Git HEAD 计算版本，CI 完整获取历史和 Tags。Pull Request 默认构建 GitHub 的合并提交，版本中的 Commit 对应这个实际 HEAD。

| 场景 | 显示版本 | 数字打包版本 |
| --- | --- | --- |
| 本地构建 / 开发 | `dev` | `build/config.yml` 的 `info.version` |
| 正式 Tag Push | Tag 原名，如 `v0.0.1` | 去掉 `v`，如 `0.0.1` |
| CI，存在祖先正式 Tag | 最近正式 Tag + 8 位 HEAD，如 `v0.0.1-a1b2c3d4` | 该正式 Tag 的数字版本 |
| CI，无祖先正式 Tag | `dev-a1b2c3d4` | 配置的数字兜底版本 |

数字打包版本用于 Windows 固定资源版本（四段，如 `0.0.1.0`）；界面、诊断信息、Windows 字符串资源和产物名称使用完整显示版本。不能把 `dev`、带 `v` 的 Tag 或 Commit 后缀直接放进 Windows 数值资源。

每次实际编译桌面可执行文件前记录 UTC RFC 3339 构建时间，通过 Go `-ldflags -X` 注入版本、时间和 Commit；原生与 Docker 构建使用同一组定义。应用通过 `ApplicationService.GetBuildInfo` 获取只读信息，界面按本地时区显示日期。获取不到 Git 信息时保留缺省值，不使用启动时间或文件时间替代。

流水线在版本 Job 中生成 `DAN_TICK_VERSION`、`DAN_TICK_PACKAGE_VERSION`、`DAN_TICK_COMMIT`，统一传给各平台。日常本地开发不需要设置这些变量，不会因为附近存在正式 Tag 就显示正式版本。

## 配置与本地打包

[build/config.yml](../build/config.yml) 的 `info` 是公司、产品名称、产品标识、描述、版权和注释的配置入口。普通目标平台构建会自动刷新对应资源：Windows EXE / NSIS 使用同步后的资源；Linux AppImage 使用实际的 `build/linux/dan-tick.desktop`。CI 版本由 Git 自动覆盖，**发布时不必修改 `info.version`**。文件顶层的 `version: '3'` 是 Wails 配置格式版本。

在仓库根目录执行：

```sh
# 当前平台生产构建，自动生成 Binding 和前端产物
wails3 build

# Windows EXE + 用户级 NSIS
wails3 task package GOOS=windows ARCH=amd64 INSTALL_SCOPE=user

# Linux 薄 AppImage：先执行普通 Linux 构建，再组装 AppImage
wails3 task linux:create:appimage ARCH=amd64

# 检查当前版本判定，无需修改配置
go run ./build/tools version
```

Windows NSIS 默认用户级安装：安装目录为 `%LOCALAPPDATA%\Programs\Dan Tick`，注册项写入 HKCU，快捷方式属于当前用户。显式使用 `INSTALL_SCOPE=machine` 才构建机器级安装器。

原始产物在 `bin/`，流水线将其复制、按版本重命名并生成校验文件后上传。本地需安装 NSIS 的 `makensis`；Linux AppImage 打包需普通 Linux / Wails 构建依赖、Bash、curl 和 git，`build/linux/appimage/build.sh` 下载并校验固定打包工具后组装薄 AppDir，不调用 Wails AppImage generator 或 linuxdeploy。发布应在 Ubuntu 24.04、目标 amd64 架构的 Linux 环境完成；其他发行版本地构建仅用于对应环境测试。非 Linux / 跨架构的普通构建仍可使用既有 Docker 交叉编译路径，AppImage 组装则需要目标架构的 Linux 环境；交叉编译二进制成功不代表宿主机可以完成打包。

`common:update:build-assets` 已改为支持平台的资源同步任务，可传 `PLATFORM=linux` 或 `PLATFORM=windows`，默认同步两者。它只更新当前目标需要的资源，保留 nFPM 等未参与本次发布的定制。直接使用 Wails 原生 `wails3 update build-assets` 仍会覆盖多个平台的模板资源，升级模板时须检查生成差异。

完成 G3 后，在准备发布的提交上创建并推送正式 Tag 即可触发发布，例如首发 `v0.0.1`。Tag 必须先存在于远端；流水线不会自动创建或移动 Tag。
