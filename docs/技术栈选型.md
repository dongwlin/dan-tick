# 技术栈选型

## 1. 定位与现状

dan-tick 是基于 Wails 3 的 Windows / Linux 本地桌面应用。业务需求与验收标准见 [PRD](PRD.md)，本文记录已确定的技术选型及其与通用 Web SPA 规范的差异。

正式应用页面与业务仍主要是 Wails 模板，但已接入 Bun、SQLite 及首个数据库 Migration；独立的 [UI 原型](../prototype/README.md) 使用 Vanilla TypeScript 和演示数据，不是正式 Vue 前端。其他选型仍需按开发计划逐步接入，不为了符合技术栈清单预先搭建空模块。

## 2. 技术选型

| 领域 | 选型 | 约定 |
| --- | --- | --- |
| 桌面框架 | Wails 3 | Windows / Linux；应用生命周期与平台能力由 Go 管理 |
| 后端 | Go 1.25（当前 `go.mod`） | 业务逻辑、调度、持久化、凭证及 B 站 HTTP 请求 |
| ORM | Bun | SQLite 数据访问、模型映射和事务 |
| 本地数据库 | SQLite + `modernc.org/sqlite` | 使用纯 Go `database/sql` 驱动、Bun SQLite Dialect |
| 数据库迁移 | Bun Migrations | 版本化迁移，优先保持 SQL 和 Schema 清晰 |
| 日志 | zerolog | 结构化诊断日志，执行记录另存 SQLite |
| 调度 | `robfig/cron/v3` | 周期计划触发；可靠性由业务层和 SQLite 保障 |
| 凭证存储 | `go-keyring` | Windows Credential Manager / Linux Secret Service |
| HTTP 客户端 | `net/http` | Go 后端访问 B 站，显式处理超时与取消 |
| Go 测试 | `testing` + testify | 单元测试、真实 SQLite 集成测试、必要时 Race Detector |
| 前端 | Vue 3 + TypeScript | Composition API、`<script setup lang="ts">` |
| 构建 | Vite 8 | 沿用 Wails 的开发、构建和 Binding 生成流程 |
| 页面路由 | Vue Router 4 | 使用 Hash History，集中维护路由表 |
| 样式 | Tailwind CSS v4 | CSS-first 配置；使用设计系统语义令牌 |
| 视觉设计 | 亚克力设计系统 | 浅色 / 深色主题、半透明材质、克制动效 |
| 交互组件 | Reka UI | 复杂交互使用成熟的无样式组件原语，由项目提供亚克力样式 |
| 图标 | `lucide-vue-next` | 统一图标包，保持一致的尺寸、线宽和无障碍标注 |
| 客户端状态 | Pinia 3 | 只管理实际需要跨组件共享的前端状态 |
| 异步数据 | `@tanstack/vue-query` 5 | Go 业务数据的查询、Mutation、缓存与失效 |
| 表单校验 | Zod 4 | 输入及外部数据边界校验，后端仍负责最终校验 |
| 复杂表单 | vee-validate 5 | 任务编辑等动态字段、条件字段和多字段错误管理 |
| 前端测试 | Vitest + Vue Testing Library | 默认使用行为测试，必要时升级为真实浏览器测试 |
| 前后端通信 | Wails Service Binding + Events | Binding 用于查询和操作，Events 用于后端主动通知 |

Node、包管理器、TypeScript、Lint 和测试工具以引入的前端基础规范为默认参考；现有 `frontend/package.json` 与工具配置还没有完成相应升级。引入或升级依赖时应验证与 Wails 3 的兼容性，并提交匹配的锁文件。

## 3. 后端职责与可靠性

- **架构**：通过 Wails Service Binding 暴露后端用例，由 Go 组合根组装业务、SQLite、调度器、凭证和第三方客户端。按实际职责分模块，优先具体类型，不引入 Gin、HTTP Server 或多层通用 Repository 接口。
- **Go 文件与模型**：目标是根目录仅保留应用入口 `main.go`（包括 `frontend/dist` 的 `go:embed`）；其余 Go 应用代码按职责放在 `internal/`，现有根目录的模板 `greetservice.go` 待业务接入时清理，`build/` 下的 Wails 平台模板文件不受此约束。Bun Model 默认可以供业务复用，写入 Binding 使用明确的 Input 类型，查询输出 DTO 按实际差异创建；业务包可直接使用 Bun，不强制 Repository 层。
- **事务与依赖**：由编排业务操作的代码管理 SQLite 事务，使用约束和原子写入保证防重；外部 HTTP、Cron 注册和 Events 不参与 SQLite 事务。其他包不反向依赖应用组合根，按需小接口，不建空包。
- **Binding 生成**：正式 Go module 为 `github.com/dongwlin/dan-tick`，当前模板的 Binding 生成在 `frontend/bindings/github.com/dongwlin/dan-tick/`；`wails3 generate bindings` 不带包路径时仅扫描根包。Service 迁入 `internal/` 后需同步调整扫描范围（例如 `./...`）和前端导入，并验证实际生成结果。
- **存储**：已接入 Bun + SQLite，驱动为纯 Go 的 `modernc.org/sqlite`，在应用启动时运行事务型迁移。数据库位于用户数据目录 `dan-tick/dan-tick.db`，使用 WAL、外键校验与单连接池；后续业务将保存任务、执行实例、调度信息和普通设置。凭证仅进入操作系统 Keyring，安全存储不可用时明确报错。
- **数据模型**：实体关系与业务含义见 [后端数据模型设计](后端数据模型设计.md)；具体 SQLite 字段、索引、外键、事务、防重及 Bun Migration 方案见 [SQLite Schema 与 Migration 设计](SQLite%20Schema%20与%20Migration%20设计.md)。六张业务表与索引已落地；业务事务仍待后续实现。
- **调度**：采用 `robfig/cron/v3` 负责计划时刻的定时唤醒，`internal/schedule.NextAfter` 按保存的 IANA 时区和本地日历规则计算每日、每周及一次性任务的 `next_due_at`。`internal/scheduler.Manager` 为每个持久化的计划时刻注册一次性 Cron 唤醒，领取成功后从 SQLite 游标重注册下一次，避免 Cron 与 A3 在夏令时缺失 / 重复时间上的差异。不向用户暴露任意 Cron 表达式；Cron 内存注册不替代 SQLite 防重与恢复。E3 已在 Cron 注册前处理遗留执行和过期游标，并提供显式睡眠恢复重建入口。
- **非敏感设置**：`internal/settings` 读写现有 `app_settings`，缺省时区为 `Asia/Shanghai`，自动调度默认开启。时区按 IANA 名称校验，只影响后续未指定时区的新任务；任务编辑缺少时区则保留原值，不因修改全局默认值改变已有计划。全局暂停在 SQLite 持久化，不改动任务启用标志与执行历史；运行中从 `scheduler.Manager.SetSchedulingEnabled` 更新以同步 Cron，计划领取事务也检查开关。恢复时先按 E3 错过规则推进过期计划，再恢复未来注册，不补发。普通设置不保存 Cookie 或其他 Keyring 凭证，正式 Binding 与 UI 在 F 阶段接入。
- **执行与防重**：调度器、执行器、B 站客户端分清职责。自动执行在 SQLite 中以任务和计划实例标识持久化登记，并通过唯一约束或原子事务防重；手动执行不修改计划。跨任务共享账号级发送频率控制。
- **错过与恢复**：Cron 本身不保证睡眠恢复后不补发。触发前必须比较计划时间与当前时间，超出业务允许的迟到窗口则记录为错过；启动和唤醒后按持久化状态恢复，不批量补发。实时 Cron 回调宽限为 30 秒，超期记录 `missed`；启动 / 显式唤醒恢复不补发已过期计划，长时间离线仅记一条代表性错过实例并直接推进未来游标。夏令时规则见 SQLite Schema 设计。
- **副作用**：发送 HTTP 请求设置超时并支持取消；结果不确定时默认不自动重试。`internal/diagnostic/` 使用 zerolog 只记录预定义的安全事件与字段，实际执行历史由 SQLite 保存。日志默认写入 `xdg.StateHome/dan-tick/logs/dan-tick.jsonl`（Linux 通常为 `~/.local/state/dan-tick/logs`，Windows 通常为 `%LOCALAPPDATA%\dan-tick\logs`），按 10 MiB / 5 个文件 / 14 天清理，写入失败不阻断业务并暴露降级状态。设置页入口与导出属于后续 L3 单元。
- **B 站接口**：MVP 所需的登录检查、直播间查询、弹幕发送参数与业务错误码见 [B 站 API 对接参考](B%20站%20API%20对接参考.md)；社区资料仅供实现参考，接口变化需在实际接入时验证。
- **测试**：用 testify 测试状态机、调度、事务与恢复；Bun 查询使用真实临时 SQLite，B 站 HTTP 使用 `httptest`。Keyring、系统睡眠、托盘和后台运行仍需 Windows / Linux 实机验证，不用 PostgreSQL Testcontainers。

## 4. 状态与数据流

- **Go 是业务事实来源**：任务、直播间、执行记录、调度状态及配置由 Go 管理并按需持久化。界面关闭或重建不能影响后台调度。
- **TanStack Query 是前端业务数据缓存**：`queryFn` 和 `mutationFn` 直接调用生成的 Wails Binding；操作成功后失效相关 Query。无需为此搭建本地 HTTP Server、REST Client 或 OpenAPI 代码生成链。
- **Wails Events 负责变更通知**：调度器主动发出任务状态等事件；前端订阅后定向失效 Query、重新读取权威数据。订阅随使用它的生命周期清理，不把 Events 当成另一份可修改的数据仓库。
- **Pinia 只管客户端共享状态**：例如跨页面的界面偏好；不要再存一份任务列表或调度状态。表单草稿、弹窗开关等局部状态优先使用 Vue `ref` / `computed`。
- **桌面环境单独适配**：调用本地 Binding 的 Query 可使用 `networkMode: 'always'`；默认不盲目重试，尤其不自动重放发送弹幕等可能产生副作用的操作。刷新以操作结果和 Events 为主，避免周期性全量轮询。

所有 B 站鉴权与 HTTP 请求由 Go 执行。Cookie 等凭证不经由普通前端 Store、Query 缓存或持久化 Web 存储保管。

## 5. 路由、表单与测试边界

### 5.1 页面路由

- **采用 Vue Router 4 的 `createWebHashHistory()`**，遵循 [Wails 3 前端路由指南](https://v3.wails.io/zh-cn/guides/routing/)；不直接套用普通网站的 HTML5 History 模式。
- 路由表统一放在 `frontend/src/app/router.ts`（落地时创建），页面按需加载。初期规划：首页 `/`、任务列表 `/tasks`、任务创建 `/tasks/new`、任务编辑 `/tasks/:id/edit`、直播间 `/rooms`、执行记录 `/history`、执行详情 `/history/:id`、设置 `/settings`。实际路由位于 `#` 后。
- 路由只代表可独立访问的界面。对话框、Popover、短暂选中状态、未提交表单内容不创建路由；筛选条件仅在确有跨页面返回或恢复需要时使用 URL 查询参数。
- 页面负责解析路由参数并向 Feature 传值。任务编辑有未保存修改时阻止意外离开并要求确认；不为普通页面预设认证守卫或复杂导航框架。
- 路由和查询参数不得包含 Cookie、令牌、完整弹幕草稿等敏感数据；桌面路由不意味着自动支持操作系统级外部深链。

### 5.2 表单

- **简单表单**（如少量账号设置、应用偏好）优先使用 Vue 响应式状态、现有组件与必要的 Zod 校验，不强制引入 vee-validate。
- **任务创建 / 编辑表单**涉及单次与循环模式、可增删排序的弹幕列表、时间与时区、条件字段和跨字段约束，使用 `vee-validate 5 + Zod 4`；创建与编辑复用同一套表单逻辑，按真实职责拆组件。
- Reka UI 提供复杂输入与弹层的交互基础，Tailwind 和亚克力设计系统负责视觉。表单库不取代组件库，也不要求每个普通输入都封装一层自定义组件。
- Schema、字段错误和表单提交逻辑放在所属 Feature。表单草稿留在本地组件 / 表单状态，不同步存入 Pinia 或 Query；提交成功后使相关 Query 失效。
- 前端校验负责即时反馈，Go 后端仍必须校验业务规则（包括调度、发送间隔与凭证）；Binding 返回的可识别字段错误映射回对应字段，其他错误在表单级展示。提交过程中阻止重复操作，失败保留输入。
- 仅当真实需要跨页面暂存草稿时再单独设计草稿恢复策略；凭证不得写入 Web 存储。

### 5.3 测试

- **默认基础**：Vitest + `@testing-library/vue` + `@testing-library/user-event`，优先验证用户看得见的状态、操作与错误反馈。纯函数或 Zod Schema 用 Vitest 单元测试；普通组件行为使用轻量 DOM 测试环境。
- **页面协作测试**：使用真实 Router、Pinia、Query Client，替换 Wails Binding / Events **外部边界**来控制返回值与通知；不 Mock 被测组件内部实现，也不为了测试引入应用内 HTTP 服务。每个测试隔离 Query Cache、Store、事件监听和计时器。
- **复杂 Vue 组件**：必要时使用 Vue Test Utils 验证 props、emit、Teleport 等特定契约；Reka UI 的键盘、Focus、Dialog 和真实 CSS 行为需要可靠浏览器验证时使用 Vitest Browser Mode，不用 jsdom 结论冒充原生 WebView 验证。
- **Storybook**：选用 `@storybook/vue3-vite`，只在开始维护一批可复用亚克力组件、需要集中检查主题与交互状态时引入；不要求每个页面或私有组件都有 Story。
- **Playwright**：只在存在稳定的浏览器端关键流程需要回归验证时引入，数量从少量高价值流程开始。浏览器 E2E 不能替代真实 Windows / Linux Wails 应用对系统托盘、窗口、凭证存储与后台运行的验证。
- **风险优先**：重点覆盖任务创建 / 编辑、条件字段、提交失败、任务状态展示、Events 驱动刷新，以及已复现的回归缺陷。Go 调度、防重、持久化和 B 站请求等业务正确性主要在 Go 侧测试，不复制成前端 E2E。
- **不默认引入**：Jest、Cypress、MSW（Wails Binding 不是 HTTP）、大面积 DOM Snapshot、固定覆盖率竞赛或为模板阶段建立完整 E2E / Storybook CI。工具开始实际使用时再加入相应脚本与 CI 检查。

## 6. 通用 specs 的适用边界

已从 [specs 仓库](specs/spec-pack-manifest.json)引入 [Vue SPA Pack](specs/packs/Vue%20SPA%20Pack.md)，叠加 [亚克力设计 Pack](specs/packs/亚克力设计%20Pack.md)，并引入 [Wails 桌面后端 Pack](specs/packs/Wails%20桌面后端%20Pack.md)。复制的规范保留上游原文，来源版本和哈希记录在 `docs/specs/spec-pack-manifest.json`。

通用规范中与桌面应用相容的原则默认遵守。以下是 dan-tick 的**明确项目级取舍**，以本文为准：

| 上游约定 | dan-tick 的处理方式 |
| --- | --- |
| SPA 通过 `fetch` / HTTP Client 访问服务端，配套 HTTP API、Orval / OpenAPI、MSW | **不适用于 Wails 本地业务调用**，统一使用 Binding；B 站 HTTP 通信封装在 Go 后端。引入的《HTTP API 设计规范》仅作为上游引用闭包，不强制实现应用内 HTTP API。 |
| Vue Router 4 与基于 URL 的页面状态 | **采用 Vue Router 4 的 Hash History**，只用作桌面应用内部页面导航，不要求所有临时 UI 状态进入 URL。 |
| Pinia、表单库、Storybook、E2E 等完整 SPA 基础设施 | Pinia Store 按需创建；任务编辑表单采用 vee-validate + Zod，简单表单不强制使用；Storybook 与 E2E 按实际需求引入，测试优先覆盖关键业务行为。 |
| 亚克力通过 CSS 背景模糊实现 | 用于应用内部界面；与操作系统桌面的原生透明 / 模糊效果单独评估，平台不支持时使用清晰可读的实心背景回退。 |
| Go API Pack 的 Gin、PostgreSQL、PASETO、HTTP Handler 与测试策略 | **不采用 Go API Pack**；后端以 Wails 桌面后端 Pack 为准，使用 Bun + SQLite、Keyring、Cron 和真实 SQLite 测试。 |

规范发生交叉或冲突时，业务范围以 `docs/PRD.md` 为准，**项目技术决策与上述例外以本文为准**；其余内容遵循 `docs/specs/` 中已引入的通用规范。未明确的技术方案保持待定，不从 Web SPA 模板推导为必须实现的功能。

## 7. 接入与维护

- 先阅读本文件，再按任务查阅 `docs/specs/packs/` 中的 Pack 及相关 Standard / Profile。
- 上游复制的规范不直接修改；项目差异记录在本文。需要同步上游规范时，使用 `specs` 仓库的 `tools/spec_pack.py copy` 更新，并以 `verify` 检查来源与本地漂移。
- 正式应用已接入 SQLite、Bun 与数据库迁移，但业务 Service 和 Vue 模板尚未替换；其他目标依赖按开发单元渐进引入。独立 UI 原型的依赖与源码不代表正式前端已经迁移完成。
