# dan-tick Roadmap

本文规划 dan-tick 的**发布版本与后续产品方向**。功能范围及验收标准以 [PRD](PRD.md) 为准；后续待办见 [待办](待办.md)；技术决策以 [技术栈选型](技术栈选型.md) 为准。

## 1. 版本规划原则

- **版本号表示交付节点，不是开发阶段编号。** 达到该版本的验收条件后才发布；不预设发布日期。
- **不为堆积功能延期。** 候选功能可以提前实现，但不得因此推迟已确定范围的版本；安全性、可靠性和 Windows / Linux 基础兼容性不能为了赶版本降低标准。
- **后续版本的目标可以调整。** `v0.0.2`、`v0.0.3`、`v0.1.0` 是当前推荐的交付顺序，不表示所有候选功能都已确定要做；每个版本在启动开发前确认范围与验收条件。
- **修复优先于版本规划。** 若出现严重缺陷，可优先使用下一可用版本号发布修复，并相应调整后续规划，不为了保持既定顺序推迟修复。

## 2. 后续版本

### v0.0.2：完善桌面常驻体验

优先目标是降低长期后台运行的使用成本：

- 开机自启动的开启 / 关闭与状态反馈；启动后隐藏只在窗口有可靠恢复入口时开放。
- 对登录失效或其他需要用户干预的情况提供恰当的额外提醒（如平台允许的系统通知）。

发布前确认 Windows / Linux 上的关闭窗口、隐藏、恢复、显式退出和系统重启行为；不能破坏 `v0.0.1` 的后台调度与发送安全性。

### v0.0.3：完善日常任务与数据体验

当前候选范围：

- 执行记录按任务、直播间、时间和状态筛选。
- 诊断日志查看、手动历史清理以及更清楚的错误说明和处理建议。
- 登录状态的附加提示与应用语言切换，按实际使用价值决定是否纳入。

本版本以**体验完善和低风险维护**为目标，不将多账号、复杂 Cron 或事件监听混入。筛选和日志功能不得泄漏凭证；清理操作不得误删任务配置。

### v0.1.0：任务管理能力的下一阶段

在前述版本可靠运行且收到真实使用反馈后，再从下列候选中选择：

- 任务模板、分组和常用配置复用。
- 任务导入 / 导出、配置备份与恢复。
- 执行统计及更清晰的历史分析。

**目前尚未形成 v0.1.0 的承诺交付清单**。决定实施时，先验证数据格式、版本兼容性、恢复失败处理和使用价值，再更新 PRD 及相应待办。

## 3. 暂未分配版本的长期方向

以下方向保留在候选池中，不预先指定 `v0.2.0` 或更高版本，以免把可行性尚未验证的设想变成版本承诺。

| 方向 | 候选能力 | 进入实施前需要验证 |
| --- | --- | --- |
| 高级调度 | 日期排除、节假日计划、有限 Cron 表达式、可控时间偏移 | 现有计划、时区、夏令时与防重语义已稳定 |
| 直播间后台持续刷新 | 已保存直播间信息的后台自动刷新 | 明确刷新范围与频率，避免接口集中请求；展示信息刷新不影响任务调度 |
| 任务编辑预览 | 编辑任务时预览执行计划 | 与实际调度使用一致的时区和计划语义，明确预览范围 |
| 直播间事件 | 开播触发、下播停止、指定直播间事件响应 | 事件来源合法可靠、断线恢复正确，不导致重复发送 |
| 账号扩展 | 多账号任务管理 | 安全存储、账号隔离、限流和失效处理能够正确演进 |
| 浏览器插件同步 | 首期 Chrome 扩展读取选定 Cookie Store 中的两个 Cookie，经配对的本地通道交给 Go | 用户主动安装、授权并配对，首次导入与重新授权由用户触发；扩展只获得 B 站所需权限，不读取 / 传播 `refresh_token`，由浏览器负责续期；任一时刻仅有一个生效的凭证来源，切换前停止旧来源的同步或续期；Go 验证 UID，账号切换时暂停覆盖并请求确认，失败不能静默丢弃有效凭证；仅在扩展运行、授权和本地连接均正常时持续同步；验证 Native Messaging 身份与消息边界、Cookie 删除再写入、Profile 切换、退出登录、连接中断及 Windows / Linux 双平台安装，不重新引入手动 Cookie 输入 |
| 更多运行形态 | 独立 Go CLI、无界面后台运行 | 确有需求，并解决凭证解锁、生命周期、部署和状态查看问题 |

现阶段不为这些方向预建插件接口、多账号架构、持久化通用队列或无界面运行服务。

## 4. 不纳入当前版本序列的事项

- 云端同步、多设备协作、Web 管理后台及移动端远程控制。
- AI 自动生成弹幕、自动回复、自动跟车或热门弹幕识别发送。
- 通用插件系统、自动更新服务及其他缺乏明确需求的平台化能力。
- 验证码绕过、风控规避、频率限制绕过等能力（不予支持）。

无论后续版本如何演进，都应保持**本地优先、凭证安全、发送可控、遵守平台规则**。

## 5. 版本范围如何调整

每次开始规划一个版本时，检查：

1. **前一个版本是否达到验收标准？** 重复发送、数据损坏、后台失控和凭证泄漏等问题优先处理。
2. **候选功能是否值得做？** 优先解决真实用户问题；不为了凑版本而添加新选项。
3. **Windows / Linux 与 B 站接口是否支持？** 明确平台差异、必要的降级和失败反馈。
4. **数据与维护成本是否可控？** 尽量避免不必要的迁移、额外后台服务或复杂抽象。

确定版本范围后，在 PRD 中确认功能与验收标准，必要时更新技术选型，再拆到待办的实施单元；未被选中的候选留在本路线图。**Roadmap 管版本方向，PRD 管产品行为，待办管执行与提交。**
