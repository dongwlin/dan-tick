# dan-tick Roadmap

本文规划 dan-tick 的**发布版本与后续产品方向**。MVP 具体范围及验收标准以 [PRD](PRD.md) 为准；实施顺序和最小可提交单元见 [开发计划](开发计划.md)；技术决策以 [技术栈选型](技术栈选型.md) 为准。

**核心约定：`v0.0.1` 是 MVP 完成后的第一个正式发布版本。** 在此之前只进行开发与原型迭代，不将尚未完成的模板应用或 UI 原型当作已经发布的 `v0.0.1`。

## 1. 版本规划原则

- **版本号表示交付节点，不是开发阶段编号。** 达到该版本的验收条件后才发布；不预设发布日期。
- **`v0.0.1` 的必要范围就是 PRD 的 P0。** P1 可以提前实现，但不为了堆积功能而延期 MVP。P0 的安全性、可靠性和 Windows / Linux 基础兼容性不能为了赶版本降低标准。
- **后续版本的目标可以调整。** `v0.0.2`、`v0.0.3`、`v0.1.0` 是当前推荐的交付顺序，不表示所有候选功能都已确定要做；每个版本在启动开发前确认范围与验收条件。
- **修复优先于版本表。** 若发布后出现严重缺陷，可优先使用下一可用版本号发布修复，并相应调整后续规划，不为了保持原表顺序推迟修复。
- **仓库中的版本字段不等于发布状态。** 当前 `build/config.yml` 的 `0.0.1` 是 Wails 模板配置，`prototype/package.json` 的版本仅属于独立原型；正式应用实际发布时再统一核对版本标识和产物。

## 2. 版本总览

| 版本 | 定位 | 主要交付内容 | 发布条件 | 状态 |
| --- | --- | --- | --- | --- |
| **v0.0.1** | **MVP / 首个正式版本** | 单账号、直播间与任务、手动 / 定时 / 循环发送、执行记录、可靠恢复及基础桌面能力 | PRD P0 与 AC-001～AC-012 验收通过；Windows / Linux 可实际运行 | 待开发 |
| **v0.0.2** | 桌面常驻体验 | 优先补齐托盘、开机自启动、启动后隐藏及必要状态提醒 | 后台运行和窗口恢复在支持的平台上可靠；不支持的环境能明确降级 | 规划中 |
| **v0.0.3** | 日常使用完善 | 执行记录筛选、编辑预览、日志与历史管理、直播间信息刷新等 P1 体验 | 不影响已有调度与发送语义，用户可理解错误与数据处理结果 | 规划中 |
| **v0.1.0** | 任务管理增强 | 依据真实需求选择任务模板、分组、导入 / 导出、配置备份与统计等能力 | 先明确要解决的问题、数据兼容与恢复策略，再确定实际交付清单 | 候选 |

### v0.0.1：MVP 首发

**必须完成：**

- **账号和直播间**：单 B 站账号凭证安全存储、状态验证、直播间添加与必要校验。
- **任务和执行**：任务创建、编辑、启用、禁用、删除；一次性 / 每日 / 每周计划；单条及有限循环发送、手动执行、停止操作与账号级发送限流。
- **可靠性与记录**：本地持久化、计划防重、异常与睡眠恢复、默认不补发错过任务、发送结果和执行详情、安全错误反馈。
- **桌面可用性**：正式 Vue / Wails 界面、后台运行、单实例、可靠的窗口恢复入口，Windows / Linux 基础兼容。
- **交付验证**：完成 [PRD 第 11 节](PRD.md#11-第一版验收标准) 的 AC-001～AC-012，构建可运行的两平台产物并完成必要的实机验证，提供最基本的安装 / 使用说明。

具体开发顺序与提交单元沿用 [开发计划 A～G](开发计划.md#3-最小可执行可提交单元)，不在 Roadmap 中重复列任务。

**非首发门槛：** 系统托盘、开机自启动、启动后隐藏、执行记录筛选、任务编辑预览等仍按 PRD 属于 P1。考虑到常驻桌面场景，**若不妨碍 P0 验收，托盘和自启动优先争取随 `v0.0.1` 交付**；否则顺延 `v0.0.2`。没有托盘时不允许将窗口隐藏到用户无法找回。

### v0.0.2：完善桌面常驻体验

优先目标是降低长期后台运行的使用成本：

- 系统托盘及常用菜单操作，兼顾不同 Linux 桌面环境的支持差异。
- 开机自启动的开启 / 关闭与状态反馈；启动后隐藏只在窗口有可靠恢复入口时开放。
- 对登录失效或其他需要用户干预的情况提供恰当的额外提醒（如平台允许的系统通知）。

发布前确认 Windows / Linux 上的关闭窗口、隐藏、恢复、显式退出和系统重启行为；不能因新增托盘破坏 `v0.0.1` 的后台调度与发送安全性。若以上功能已经在首发实现，本版本优先处理实机反馈和遗留问题，不重复开发。

### v0.0.3：完善日常任务与数据体验

当前候选范围来自 [PRD 的 P1](PRD.md#12-开发优先级)：

- 执行记录按任务、直播间、时间和状态筛选；任务编辑时展示预计执行信息。
- 诊断日志查看、手动历史清理以及更清楚的错误说明和处理建议。
- 登录状态的附加提示、直播间信息自动刷新与应用语言切换，按实际使用价值决定是否纳入。

本版本以**体验完善和低风险维护**为目标，不将多账号、复杂 Cron 或事件监听混入。筛选和日志功能不得泄漏凭证；清理操作不得误删任务配置。

### v0.1.0：任务管理能力的下一阶段

在前述版本可靠运行且收到真实使用反馈后，再从下列候选中选择：

- 任务模板、分组和常用配置复用。
- 任务导入 / 导出、配置备份与恢复。
- 执行统计及更清晰的历史分析。

这些能力来自 [PRD 第 13 节](PRD.md#13-后续扩展方向)，**目前尚未形成 v0.1.0 的承诺交付清单**。决定实施时，先验证数据格式、版本兼容性、恢复失败处理和使用价值，再更新 PRD 及相应开发计划。

## 3. 暂未分配版本的长期方向

以下方向保留在候选池中，不预先指定 `v0.2.0` 或更高版本，以免把可行性尚未验证的设想变成版本承诺。

| 方向 | 候选能力 | 进入实施前需要验证 |
| --- | --- | --- |
| 高级调度 | 日期排除、节假日计划、有限 Cron 表达式、可控时间偏移 | 现有计划、时区、夏令时与防重语义已稳定 |
| 直播间事件 | 开播触发、下播停止、指定直播间事件响应 | 事件来源合法可靠、断线恢复正确，不导致重复发送 |
| 账号扩展 | 二维码登录、账号状态自动刷新、多账号任务管理 | 安全存储、账号隔离、限流和失效处理能够正确演进 |
| 更多运行形态 | 独立 Go CLI、无界面后台运行 | 确有需求，并解决凭证解锁、生命周期、部署和状态查看问题 |

现阶段不为这些方向预建插件接口、多账号架构、持久化通用队列或无界面运行服务。

## 4. 不纳入当前版本序列的事项

- 云端同步、多设备协作、Web 管理后台及移动端远程控制。
- AI 自动生成弹幕、自动回复、自动跟车或热门弹幕识别发送。
- 通用插件系统、自动更新服务及其他缺乏明确需求的平台化能力。
- 验证码绕过、风控规避、频率限制绕过等能力（不予支持）。

无论后续版本如何演进，都应保持**本地优先、凭证安全、发送可控、遵守平台规则**。

## 5. 版本范围如何调整

每次开始规划一个版本时，检查：

1. **前一个版本是否达到验收标准？** 重复发送、数据损坏、后台失控和凭证泄漏等问题优先处理。
2. **候选功能是否值得做？** 优先解决真实用户问题；不为了凑版本而添加新选项。
3. **Windows / Linux 与 B 站接口是否支持？** 明确平台差异、必要的降级和失败反馈。
4. **数据与维护成本是否可控？** 尽量避免不必要的迁移、额外后台服务或复杂抽象。

确定版本范围后，在 PRD 中确认功能与验收标准，必要时更新技术选型，再拆到开发计划的最小可提交单元；未被选中的候选留在本路线图。**Roadmap 管版本方向，PRD 管产品行为，开发计划管执行与提交。**
