# 前端交互与可访问性规范

## 1. 适用范围

本规范适用于基于 Vite、TypeScript 的 React 与 Vue Web 应用，规定页面、表单、反馈、导航、弹层、键盘、触摸、动效和辅助技术的统一交互要求。

本文是前端交互行为与可访问性验收的权威规范：

- 共享技术基线与框架专属选型由项目采用的技术 Profile 定义
- 页面、Feature 和组件职责见《[[前端应用架构规范]]》
- 测试工具、Storybook 与 E2E 分层见《[[前端测试规范]]》
- API 错误分类以 HTTP 契约为准；认证恢复与重放由项目选择的认证 Profile 定义
- 颜色、间距和 Design Token 的具体实现由项目设计系统规定

规范中的“必须”是发布门槛，“应该”是默认执行、只有明确理由才能偏离的项目约定，“可以”表示按场景选择。

## 2. 合规目标

### 2.1 WCAG 2.2 AA 是发布基线

所有新增完整页面和业务流程必须达到 WCAG 2.2 AA；可复用组件必须满足适用的成功标准，且不能让所在页面产生新的失败。验收对象不是单个静态截图，而是用户完成任务所经过的完整过程，包括弹窗、错误状态、身份验证、超时恢复和异步结果。

项目优先满足以下四类目标：

- **可感知**：信息不只依赖颜色、位置、形状、声音或动画表达
- **可操作**：键盘、触摸、鼠标和辅助技术都能完成同一任务
- **可理解**：导航、文案、校验和状态变化可预测
- **健壮**：名称、角色、状态和值能被浏览器与辅助技术正确识别

组件库通过无障碍测试不代表业务页面自动合规。业务代码仍需提供正确标签、文案、焦点流、错误处理和状态反馈。

### 2.2 项目增强要求

以下要求高于或细化 WCAG 2.2 AA，作为本项目默认质量线：

- 指针与触摸目标默认至少为 `44 × 44 CSS px`；除 WCAG 明确允许的例外外，`24 × 24 CSS px` 是无法达到默认尺寸时的绝对底线
- 所有可交互元素都具有清晰、一致且不被遮挡的 `:focus-visible` 样式
- 所有拖拽、滑动、长按和多点手势都有点击与键盘替代方式
- 所有重要状态变化同时提供视觉反馈和辅助技术可感知的反馈
- 动效在 `prefers-reduced-motion: reduce` 下保留状态含义，但移除不必要的位移、缩放和循环运动
- 关键流程至少经过键盘、缩放、真实浏览器和一种主流屏幕阅读器人工验证

### 2.3 例外处理

暂时无法满足某项要求时，必须登记：

- 受影响的用户与流程
- 对应 WCAG 条款或项目约定
- 当前替代方式
- 修复负责人和期限
- 自动化规则为何无法覆盖

第三方组件、嵌入内容和遗留页面不能因为“不由本项目维护”而静默豁免。至少保证它们不阻断整个流程，并提供等价替代路径。

## 3. 核心原则

### 3.1 原生语义优先

能用原生 HTML 表达时，不用 `div`、`span` 和自定义 ARIA 模拟：

```html
<a href="/tasks">查看任务</a>
<button type="button">创建任务</button>
```

- 导航使用 `<a>` 或 Router Link，保留新标签页、复制链接和浏览器历史能力
- 原地执行动作使用 `<button>`
- 表格数据使用 `<table>`，列表使用 `<ul>` / `<ol>`
- 表单控件使用 `<label>`、`fieldset` 和 `legend`
- 页面使用 `header`、`nav`、`main`、`aside` 和 `footer` 等 Landmarks

遵循“没有 ARIA 好过错误 ARIA”。只有原生语义不足时才添加 ARIA，并确保名称、角色、状态和值随真实 UI 同步。

### 3.2 输入方式平等

任何可通过鼠标完成的功能都必须能通过键盘完成。任何依赖 Hover、拖拽、滑动、路径手势或设备运动的功能，都必须提供不依赖该输入方式的替代操作。

不得通过 User Agent 判断用户使用鼠标还是触摸。界面应允许用户在键盘、鼠标、触控笔和触摸之间随时切换。

### 3.3 状态必须可见、可理解、可恢复

用户执行操作后，界面必须回答：

1. 操作是否已经接收？
2. 当前是否仍在处理？
3. 最终成功还是失败？
4. 失败后可以如何继续？
5. 是否可以撤销或重试？

不允许出现点击无反馈、无限 Loading、错误后清空输入、后台失败却弹出无上下文 Toast 等行为。

### 3.4 不制造意外

- Focus 本身不得自动提交、导航或打开新窗口
- 选择 Select、Radio 或 Checkbox 时，除非控件已明确说明，不立即跳转页面
- 自动刷新不得打断输入、重置滚动或抢夺焦点
- 后台数据更新不得静默覆盖用户未保存的编辑
- 权限变化、会话失效和冲突必须解释原因与下一步

### 3.5 组件行为一致

同一语义在整个应用中保持一致：

- 相同图标、名称和位置执行相同动作
- 主要操作、危险操作、返回与取消的视觉层级一致
- Loading、Empty、Error、Offline 和 Forbidden 状态使用统一模式
- Dialog、Menu、Tabs、Toast 和表单错误的键盘与焦点行为一致

## 4. 交互元素

### 4.1 动作与导航

按钮文案必须描述结果，例如“保存任务”“邀请成员”“删除项目”，不要使用脱离上下文的“确定”“继续”“点击这里”。

链接文本应在脱离周围段落时仍能说明目的。相同文本不得指向不同目标；相同目标也不应使用含义矛盾的名称。

图标按钮必须有可访问名称：

- 首选同时展示文字
- 空间受限时提供 `aria-label`
- Tooltip 只用于补充说明，不能作为唯一可访问名称
- 装饰图标使用 `aria-hidden="true"`
- 图标旁已有可见文字时，不让图标重复进入无障碍树

### 4.2 交互状态

可复用交互组件至少定义并验证：

- Default
- Hover
- Focus Visible
- Active / Pressed
- Disabled 或 Read-only
- Loading
- Error
- Success（如果成功状态会留在组件内）

Hover、Focus 和 Active 必须可区分，不能只通过轻微透明度变化表达。状态颜色必须使用语义 Token，并在浅色、深色和高对比度环境中保持可辨识。

### 4.3 Disabled、Read-only 与 Loading

- 无法操作且无需 Focus 的原生控件使用 `disabled`
- 内容可读取、复制但不可编辑时使用 `readonly`
- 需要保留在 Tab 顺序中并解释不可用原因时，可以使用 `aria-disabled="true"`，但代码必须阻止实际操作
- 不把权限不足伪装成 Disabled；应展示权限原因或明确的 Forbidden 状态
- 不把所有不可用原因藏在 Disabled 控件的 Tooltip 中，因为该控件可能无法获得 Hover 或 Focus

请求开始前提交按钮保持可用；请求进入 Pending 后阻止重复提交，保留原有可访问名称并补充处理中状态。Loading 不得造成按钮宽度跳变或让用户误以为操作消失。

### 4.4 点击与触摸目标

- 默认目标尺寸至少 `44 × 44 CSS px`
- 相邻目标之间保留足够间距，避免误触
- Checkbox、Radio 与其完整 Label 共同构成点击区域
- 小图标可以视觉上小于目标，但可点击区域不得随之缩小
- 触摸设备不能依赖 Hover 才暴露必要操作
- 禁止通过 `user-scalable=no` 或 `maximum-scale=1` 关闭页面缩放

连续正文中的内联链接可以不强制撑到 `44 × 44 CSS px`，但必须依靠足够行高、间距、下划线或其他非颜色线索保持可发现且不易误触。其他紧凑场景即使适用 WCAG 的尺寸或间距例外，也应先尝试扩大不可见点击区域。

列表行整体可点击时，行内按钮和链接必须保持独立语义，避免嵌套交互元素和事件冒泡导致误操作。

## 5. 键盘与焦点

### 5.1 Tab 顺序

Tab 顺序必须跟随 DOM 和视觉阅读顺序：

- 禁止使用正数 `tabindex`
- 非交互元素不加入 Tab 顺序
- 暂时隐藏或不可交互的内容不得仍可获得焦点
- 复合组件内部使用组件库提供的 Roving Tabindex 或 `aria-activedescendant` 模式
- 页面不能形成键盘陷阱；只有 Modal Dialog 可以在打开期间限制焦点范围

方向键、Home、End、Enter、Space 和 Escape 的行为遵循对应 WAI-ARIA APG Pattern，不自行发明不一致的键位。

### 5.2 Focus 样式

所有键盘可操作元素都必须显示清晰的 Focus Indicator：

- 使用 `:focus-visible` 区分键盘 Focus 与普通指针点击
- 不使用没有替代样式的 `outline: none`
- Focus Indicator 与相邻颜色的对比度至少为 `3:1`
- Sticky Header、Bottom Bar、Cookie Banner、Drawer 和软键盘不得完全遮挡当前 Focus
- 锚点标题设置合适的 `scroll-margin-top`，避免定位后被固定 Header 覆盖

点击产生的 Focus 不应因为“看起来不好看”而被脚本立即 Blur。Focus 是状态，不是视觉瑕疵。

### 5.3 Focus 移动

只有用户上下文发生明确变化时才主动移动 Focus：

- 打开 Dialog → 移入 Dialog 内合适的首个元素或标题
- 关闭 Dialog → 返回触发元素；触发元素已不存在时移到合理后继位置
- 提交失败 → 移到错误摘要或首个无效字段
- 删除当前项 → 移到下一项、上一项或列表标题，不能丢到 `body`
- SPA 完成页面级导航 → 更新页面标题，并把 Focus 放到新页面主标题或主内容入口

筛选、分页、Tab 切换等局部 URL 更新不应机械把 Focus 重置到页面顶部。程序化 Focus 的目标若不是原生可聚焦元素，可临时使用 `tabindex="-1"`。

### 5.4 快捷键

- 快捷键必须可发现，并在 Menu 或帮助区域展示
- 单字符快捷键必须允许关闭、重新映射，或只在目标控件 Focus 时生效
- 不覆盖浏览器和辅助技术的常用快捷键
- 快捷键使用平台正确的修饰键提示
- 操作结果仍需通过普通按钮或菜单完成，快捷键只是加速路径

## 6. 页面与导航

### 6.1 页面结构

每个路由页面必须具有：

- 准确且随路由更新的 `document.title`
- 一个描述页面主题的主 `h1`
- 层级连续、不过度依赖字号模拟的 Heading 结构
- 唯一主内容 Landmark
- 可跳过重复导航、直达主内容的 Skip Link
- 与视觉顺序一致的 DOM 阅读顺序

多个同类 `nav`、`aside` 或表单 Landmark 必须拥有可区分的可访问名称。

### 6.2 URL 与浏览器行为

可分享、可恢复的筛选、分页、排序、搜索词和 Tab 状态写入 URL。浏览器 Back / Forward 必须恢复相应界面状态，不产生重复提交或错误 Toast。

内部导航使用真实链接，保留：

- Cmd / Ctrl + Click
- 中键打开
- 复制链接
- 在新标签页打开
- 浏览器状态栏预览目标

不得用 `onClick` + `navigate()` 模拟普通链接。

### 6.3 未保存内容

离开存在未保存内容的页面前必须提醒用户，但不要对没有真实修改的表单重复确认。成功保存、明确放弃或内容恢复后立即清除阻止条件。

浏览器关闭只使用简短的原生 `beforeunload` 提醒；应用内导航可以提供包含“继续编辑”“放弃更改”的可访问 Dialog。

## 7. 复合组件与弹层

### 7.1 优先复用组件系统

Dialog、Alert Dialog、Popover、Menu、Tabs、Tooltip、Select、Combobox 等复杂控件优先使用项目所选组件系统提供的可访问实现，不从 `div` 和 ARIA 属性手写完整交互模型。具体组件系统由对应框架 Profile 定义。

组件系统负责基础角色、键盘与焦点模型；业务代码仍负责：

- 清晰的 Label、Description 和错误信息
- 打开与关闭条件
- 初始 Focus 与关闭后的 Focus 恢复
- Loading、Empty、Forbidden 和冲突状态
- 业务操作的危险程度与确认方式

升级组件系统或其可访问性基础依赖后，必须回归键盘、屏幕阅读器和 Portal 类场景，不能假设第三方升级不会改变行为。

### 7.2 Dialog 与 Alert Dialog

- Dialog 必须拥有可访问标题；描述信息按需关联
- 打开后背景内容不可交互，滚动锁定不能导致布局明显跳动
- Focus 保持在 Dialog 内，Tab 和 Shift + Tab 可以完整循环
- Escape 默认关闭普通 Dialog
- 正在提交且关闭会丢失数据时，可以暂时拦截关闭，但必须说明原因
- 关闭后 Focus 返回触发元素或合理后继元素
- Alert Dialog 用于不可逆或高风险确认，初始 Focus 通常放在安全操作，而不是危险操作
- 移动端 Dialog / Drawer 必须处理软键盘、Safe Area 和内容滚动

不要使用 Dialog 展示可以直接在页面内完成的简单信息，也不要层叠多个 Modal。

### 7.3 Popover、Menu 与 Tooltip

Popover 包含交互内容时，必须建立清楚的打开、关闭和 Focus 策略。点击外部和 Escape 的关闭行为要一致，关闭后不能丢失 Focus。

Menu 用于一组操作命令；普通网站导航仍使用链接列表，不为视觉效果滥用 `role="menu"`。Menu 的方向键、Home、End、Enter、Space 和 Escape 行为遵循 APG。

Tooltip：

- 只提供补充说明，不承载必须完成的操作
- 同时支持 Hover 与 Focus
- 用户可以在不移动 Focus 的情况下按 Escape 关闭
- 内容出现后保持足够稳定，允许用户移动指针到内容区域
- 不能代替 Label、错误信息或 Disabled 原因的唯一入口

### 7.4 Tabs、Disclosure 与 Combobox

- Tabs 使用正确的 `tablist`、`tab`、`tabpanel` 关系
- 自动激活只用于内容能够无延迟展示的 Tabs；加载明显时使用手动激活
- Disclosure 的触发器是 Button，并暴露展开状态
- Combobox、Autocomplete 和 Select 不自行拼装键盘行为，优先使用项目组件系统提供的可访问 Primitive
- 搜索建议必须清楚区分输入值、当前高亮项和已选择值
- 动态结果数量可以使用克制的 Status Message 告知辅助技术，不逐字符重复播报

### 7.5 Toast 与状态消息

Toast 适合短暂、非阻塞且不需要立即决策的反馈。以下信息不得只放 Toast：

- 表单字段错误
- 权限不足
- 需要用户选择的冲突
- 无法自动恢复的会话失效
- 会导致数据丢失的失败

普通成功或后台状态使用 `role="status"` / Polite Live Region；需要立即处理的阻塞错误才使用 `role="alert"`。不要让多个重复 Toast 连续打断屏幕阅读器。

包含关键操作的 Toast 不应快速自动消失；必须允许 Focus、Hover 或用户设置延长阅读时间。Toast 消失后，其结果仍应能从页面状态或历史记录确认。

Live Region 应预先存在于 DOM，再更新其文本；不要在结果产生后同时挂载容器和完成消息并假设所有辅助技术都会播报。

### 7.6 数据表格与列表

- 关系型数据使用语义 Table，并提供描述用途的 Caption 或附近标题
- Header Cell 使用正确的行列关系；跨行跨列时保持表头关联可理解
- 排序操作放在表头 Button 中，并通过 `aria-sort` 表达当前方向
- 行级图标操作的 Accessible Name 包含当前行对象，例如“删除任务：修复登录问题”
- 选择行时同时表达选中状态和已选数量，不只改变背景色
- 分页控件使用 Navigation Landmark，并为当前页提供 `aria-current="page"`
- 响应式布局不能把 Table 视觉改成卡片后丢失字段名称与值的关系

大型列表使用虚拟化时仍需保证键盘导航、Focus 恢复、总数量和当前位置可理解；无法可靠做到时，应使用分页或分段加载。

## 8. 表单

### 8.1 Label 与输入目的

每个表单控件必须具有持久可见的 Label。Placeholder 只能展示格式示例，不能代替 Label。

输入控件应设置：

- 稳定且有意义的 `name`
- 正确的 `type`
- 移动端适用的 `inputmode`
- 符合实际字段含义的 `autocomplete`
- 必要的说明文本和格式要求

Label 的可见文字应包含在 Accessible Name 中。Required 状态同时通过文字或统一符号说明，不能只依赖颜色。

### 8.2 输入自由

- 不阻止粘贴、复制、密码管理器和系统自动填充
- 邮箱、用户名、验证码等字段按内容合理关闭拼写检查和自动大写
- 不在每次按键后自动格式化到光标跳动
- 不因空格、连字符或本地化格式制造无意义失败
- 用户输入很长、字体放大或错误文案换行时，布局仍可用

格式化显示值与提交值不同时，必须保证用户可以理解并编辑原始内容。

### 8.3 校验时机

首次输入前不展示错误。默认校验顺序：

1. 用户离开已编辑字段时，展示该字段错误
2. 用户再次输入时，及时清除已经修复的错误
3. 提交时校验全部字段，并展示错误摘要
4. 服务端返回字段错误时，映射到对应控件

校验不得在用户输入每个字符时不断抢焦点、播报或弹 Toast。密码强度、字符计数等连续反馈使用非阻塞 Status Message，并避免重复播报完整内容。

### 8.4 错误表达

错误必须同时说明问题和修复方式，例如“标题不能超过 100 个字符，请删除 12 个字符”，不要只写“参数错误”。

- 错误紧邻对应字段
- 控件使用 `aria-invalid="true"`
- 错误通过稳定 ID 与控件关联
- 页面存在多个错误时，在表单顶部提供可聚焦错误摘要
- 摘要中的每一项链接到对应字段
- 提交失败后保留用户已输入内容
- 通用服务端错误显示在表单级区域，不伪装成某个字段错误

仅用红色边框不构成完整错误提示。

### 8.5 提交与重复操作

- 点击提交后立即提供 Pending 反馈
- Pending 期间阻止同一操作重复触发
- 不清空表单，直到服务端确认成功
- 网络错误时保留内容并提供重试
- 成功后明确说明结果和下一步
- 写请求在认证恢复后的重放遵循项目选择的认证 Profile，UI 不额外提交第二次

高风险提交应在服务端提供幂等或冲突保护，前端 Disabled 只能改善体验，不能作为唯一防重机制。

### 8.6 认证表单

认证流程必须支持密码管理器、粘贴和自动填充：

- 用户名使用 `autocomplete="username"`
- 当前密码使用 `autocomplete="current-password"`
- 新密码使用 `autocomplete="new-password"`
- 一次性验证码使用 `autocomplete="one-time-code"`
- 密码规则在输入前可见，并允许显示 / 隐藏密码
- 不要求用户完成无法复制、无法使用密码管理器的认知测试
- CAPTCHA 必须有可访问替代方式

会话超时或重新认证后默认恢复用户原来的任务和未保存输入；只有安全约束或数据冲突使恢复不安全时才放弃恢复，并明确告知用户。

## 9. 异步、反馈与错误恢复

### 9.1 Loading

Loading 反馈应与等待时长和范围匹配：

- 极短操作避免闪烁 Spinner
- 局部请求只标记受影响区域，不冻结整个页面
- 首次内容加载可以使用 Skeleton，但 Skeleton 形状应接近最终结构
- 无法估算进度时使用不确定状态；可估算时展示实际进度
- 超过合理等待时间时说明正在做什么，并提供取消、后台继续或重试方式

容器正在更新时可以使用 `aria-busy="true"`。不要把每一帧进度都播报给屏幕阅读器；只播报关键阶段或完成结果。

### 9.2 Success

成功反馈应靠最终界面状态证明，而不是只弹“成功”Toast：

- 新建后显示新资源或提供可访问链接
- 修改后更新对应字段和时间
- 删除后从列表移除，并把 Focus 移到合理位置
- 后台保存显示最近保存状态

如果操作可撤销，优先提供有明确期限的 Undo；Undo 控件不能在用户有机会操作前消失。

### 9.3 Error、Offline 与冲突

错误展示位置按作用域决定：

- 字段问题 → 字段旁
- 表单问题 → 表单级区域
- 局部资源失败 → 对应区域内
- 页面无法加载 → 页面级 Error State
- 全局断网或服务不可用 → 全局但不反复弹出的状态

错误文案必须包含可执行下一步，如重试、返回、重新登录、联系管理员或解决冲突。技术堆栈、Token、原始响应和内部错误码不得直接展示给普通用户。

编辑冲突不得静默覆盖。界面应说明哪些内容已变化，并允许重新加载、比较、复制当前输入或再次提交。

### 9.4 危险操作

删除、撤销权限、覆盖数据等危险操作必须根据可恢复性选择保护：

- 容易恢复 → 执行后提供 Undo
- 难以恢复 → 执行前使用 Alert Dialog 确认
- 极高风险 → 要求输入资源名称或完成第二步确认

确认文案必须具体说明对象和后果，危险按钮使用动作名称，例如“删除项目”，不使用模糊的“确定”。取消操作应容易找到且不会导致数据变化。

## 10. 视觉可感知性

### 10.1 对比度

最低要求：

- 普通文字与背景对比度至少 `4.5:1`
- 大号文字（至少 `24 CSS px`，或至少 `18.66 CSS px` 且加粗）至少 `3:1`
- 控件边界、图标和表达状态的非文字视觉信息至少 `3:1`
- Disabled 且确实不可操作的控件不纳入最低对比度条款，但仍应可辨识

浅色、深色、Hover、Focus、Selected、Error 和 Forced Colors 环境都必须分别验证。不能只验证 Design Token 的原始颜色，而忽略透明度、叠加背景和实际组件状态。

### 10.2 不只依赖颜色

成功、警告、错误、选中和状态差异必须至少再通过一种方式表达：

- 文字
- 图标与可访问名称
- 形状或 Pattern
- 位置和结构

图表必须提供 Label、Legend 和可访问的数据替代；不能要求用户仅凭红绿区分结果。

### 10.3 缩放、重排与文字间距

- 页面在 `200%` 文字缩放下不得丢失内容或功能
- 页面在等效 `320 CSS px` 宽度或 `400%` 浏览器缩放下应单列重排
- 除表格、地图、时间轴等本质二维内容外，不产生双向滚动
- 用户调整行高、字间距和段间距后，内容不得被裁切或重叠
- 不用固定高度容纳可能换行的正文、按钮或错误信息
- 长 URL、文件名、用户生成文本和本地化文案必须安全换行或截断，并提供完整内容访问方式

### 10.4 图片、图标与媒体

- 信息图片提供与当前上下文匹配的 `alt`
- 装饰图片使用空 `alt`，不重复周围文字
- 复杂图表提供简短替代文本和详细数据说明
- 图片声明尺寸或宽高比，避免内容跳动
- 预录视频提供字幕；只有音频提供文字稿
- 自动播放声音默认禁止
- 自动播放或持续运动超过 5 秒的内容提供暂停、停止或隐藏控制

不要在 `alt` 中重复“图片”“图标”等辅助技术已经知道的信息。

## 11. 动效

### 11.1 动效必须服务于理解

动效只用于说明：

- 元素从哪里出现或消失
- 状态如何变化
- 操作影响了哪个对象
- 页面层级和空间关系

不要为普通 Hover、每次滚动或所有列表项加入装饰性大幅运动。动画期间用户仍应能够点击、滚动、按 Escape 或切换页面；动效不能阻塞任务。

### 11.2 默认时长

以下是项目体验基线，不是 WCAG 数值要求：

- 微交互反馈：`100–200ms`
- Popover、Menu、Dialog：`150–250ms`
- 页面级或较大区域过渡：`200–400ms`

退出动画通常不长于进入动画。不要使用 `transition: all`；只声明实际变化的属性。优先动画 `transform` 和 `opacity`，避免持续触发布局和重绘的属性。

### 11.3 Reduced Motion

检测 `prefers-reduced-motion: reduce` 后：

- 移除视差、大幅平移、缩放、旋转和循环装饰动画
- 保留必要的即时淡入、状态颜色或其他非运动反馈
- Skeleton Shimmer 改为静态或低运动状态
- 自动播放装饰视频显示静态 Poster
- 不用全局 `0.01ms` 强制关闭所有 Transition，因为它会破坏有意义的状态反馈

任何内容不得每秒闪烁三次以上或接近已知危险阈值。

## 12. 响应式、移动端与手势

### 12.1 响应式不是缩小桌面

窄屏下应重新安排优先级：

- 主操作保持可发现
- 次要操作可以进入 Menu，但不能消失
- 表格选择卡片、横向滚动或列优先级方案时，保持表头与数据关系
- Dialog 在窄屏可切换为 Drawer / Sheet，但语义和 Focus 规则不变
- 固定底栏考虑 Safe Area
- 软键盘打开后，当前输入与主要提交操作仍可见

不锁定横竖屏方向，除非方向对功能本身必不可少。

### 12.2 Hover 与触摸

- Hover 只作为增强反馈，不承载唯一内容或操作
- Tooltip 在触摸设备上不能是获取关键信息的唯一方式
- `pointer: coarse` 环境扩大目标与间距
- 不因隐藏系统点击高亮而删除所有按压反馈
- 避免在移动端自动 Focus 输入框并意外弹出键盘；只有单一、明确且用户预期的输入任务可以例外

### 12.3 拖拽与复杂手势

所有拖拽排序或移动必须提供等价操作，例如：

- “上移”“下移”“移到顶部”按钮
- 打开 Menu 选择目标位置或分组
- 键盘抓取、移动和放下模式

拖拽过程中必须提供当前对象、目标位置和完成结果反馈。触摸 Drag Handle 满足目标尺寸，不能让滚动与拖拽互相争抢。

滑动删除、双击、长按、捏合和设备摇动都必须有普通 Button / Menu 替代，除非手势本身是功能本质。

## 13. 内容、认知与国际化

### 13.1 文案

- 使用用户熟悉的业务词汇，不暴露内部实现术语
- 错误说明“发生了什么”和“接下来怎么做”
- Loading 文案说明正在处理的对象
- 空状态解释为什么为空，并在适用时提供主操作
- 删除、提交和授权等按钮明确说明结果
- 帮助入口在不同页面保持一致位置和名称

不要用只有视觉方向的信息，如“点击右边的红色按钮”。应引用控件名称。

### 13.2 时间限制与认知负担

- 非安全必要流程不设置短时限
- 有时限时提前告知，并允许延长或重新开始
- 多步骤流程显示当前位置，并保留已完成输入
- 不要求重复输入系统已经拥有的信息
- 重新认证后恢复原任务
- 验证码支持自动填充、粘贴和清晰的重新发送机制

### 13.3 语言与本地化

- 页面设置正确的 `lang`
- 页面内切换语言的片段标注对应语言
- 日期、时间、数字和货币使用 `Intl`，不硬编码格式
- 组件支持文案扩展、换行和可能的 RTL
- 代码、品牌名和标识符可使用 `translate="no"` 防止错误机器翻译
- 不能把英文单词长度当作按钮、Tab 或表格列宽上限

## 14. 实现边界

### 14.1 组件系统边界

- 复杂交互优先复用框架 Profile 指定的组件系统或可访问性 Primitive
- 不覆盖组件库的键盘事件、Focus 管理和 ARIA，除非已经确认默认行为不符合业务语义
- 自定义样式必须保留 Focus、Selected、Disabled、Invalid 和 Forced Colors 状态
- Portal 类内容仍属于当前交互流程，必须正确处理 Label、Focus、滚动和测试清理

没有现成组件时，先查对应 WAI-ARIA APG Pattern，再决定是否实现自定义 Widget。业务 Feature 不应各自复制 Dialog、Combobox 或 Menu 基础设施。

### 14.2 ARIA 状态

- `aria-expanded`、`aria-selected`、`aria-checked`、`aria-current` 和 `aria-busy` 必须反映真实状态
- `aria-controls`、`aria-labelledby` 和 `aria-describedby` 指向稳定且唯一的 ID
- 隐藏内容同时从视觉和无障碍树中正确移除
- 视觉上隐藏但需供辅助技术读取的文本使用统一 Visually Hidden 工具
- 不在不可交互元素上添加交互角色来绕过语义组件
- 不重复设置原生元素已经提供的 Role

### 14.3 性能不能破坏可访问性

- Virtual List 必须维持合理的 Focus、位置和总数量信息
- Lazy Content 获得 Focus 前必须确保已经渲染
- Skeleton 不能替代最终 Heading 和 Landmark 结构
- 代码分割失败要展示可恢复错误，而不是空白页面
- 乐观更新回滚后要让用户感知结果
- 不为减少重渲染而冻结 Accessible Name 或 ARIA State

## 15. 测试与发布门槛

具体测试组织与命令见《[[前端测试规范]]》。可访问性必须同时经过自动化和人工验证；任何单一工具都不能证明 WCAG 合规。

### 15.1 自动化测试

- ESLint 使用框架 Profile 指定的可访问性规则检查明显问题
- Testing Library 优先通过 Role、Label 和 Accessible Name 查询
- Vitest + `user-event` 覆盖键盘、Focus、错误关联和状态变化
- Storybook 为 Default、Focus、Disabled、Loading、Error、长文案、窄视口和深色主题建立代表性 Story
- `@storybook/addon-a11y` 对新增共享组件和关键 Story 使用阻断模式
- Browser Mode 验证真实 Focus、Popover、Dialog、CSS 和浏览器行为
- Playwright 覆盖关键流程的键盘路径、页面标题、Focus 去向和错误恢复

自动化测试不得只断言 ARIA 属性存在，还要验证用户是否能完成行为。

### 15.2 人工验证矩阵

新增关键页面和复杂组件至少验证：

1. 只使用键盘完成正常、错误和取消路径
2. Focus 顺序、可见性、Dialog 限制与关闭后恢复
3. 浏览器 `200%` 文字缩放与 `400%` 页面缩放
4. `prefers-reduced-motion`、浅色、深色和高对比度 / Forced Colors
5. 桌面窄窗口与真实触摸视口
6. 一种主流桌面屏幕阅读器组合，例如 NVDA + Firefox / Chrome，或 VoiceOver + Safari
7. 认证、表单错误、异步状态和危险操作的播报顺序

涉及字幕、语音输入、Switch Control 或特定辅助设备的功能，应增加对应用户与设备验证。

### 15.3 缺陷级别

| 级别 | 定义 | 发布要求 |
| --- | --- | --- |
| P0 | 无法完成核心任务、键盘陷阱、危险闪烁、数据不可恢复 | 立即阻断发布 |
| P1 | WCAG 2.2 A / AA 失败，或关键流程对某类输入方式不可用 | 修复后发布 |
| P2 | 项目增强要求失败，但存在清晰替代路径 | 记录并排期 |
| P3 | 不阻碍任务的体验一致性或精细度问题 | 按优先级优化 |

不得通过关闭 axe 规则、增加无意义 `aria-label` 或跳过 Story 来隐藏 P0 / P1。确认为工具误报时，应记录真实语义和人工验证证据。

## 16. Definition of Done

### 语义与键盘

- [ ] 动作使用 Button，导航使用 Link？
- [ ] Heading、Landmark、列表、表格和表单语义正确？
- [ ] 所有功能可以只用键盘完成？
- [ ] 没有正数 `tabindex`、键盘陷阱和不可见 Focus？
- [ ] SPA 导航、Dialog 和删除后的 Focus 去向合理？

### 表单与反馈

- [ ] 控件具有持久 Label、正确输入类型和 `autocomplete`？
- [ ] 允许粘贴、密码管理器和系统自动填充？
- [ ] 错误与字段关联，并说明修复方法？
- [ ] Loading、Success、Error、Offline 和冲突状态均可恢复？
- [ ] Toast 没有承载唯一的关键错误或操作？

### 视觉与输入方式

- [ ] 文字、控件和 Focus 对比度达标？
- [ ] 信息不只依赖颜色、Hover、声音或动画？
- [ ] 默认触摸目标达到 `44 × 44 CSS px`？
- [ ] `320 CSS px`、放大文字、长文案和软键盘下仍可用？
- [ ] 拖拽与复杂手势具有点击和键盘替代？
- [ ] Reduced Motion 下状态变化仍可理解？

### 验证

- [ ] Storybook 具有关键状态与窄视口 Story？
- [ ] axe、Vitest、Browser Mode 和受影响 E2E 已通过？
- [ ] 已完成键盘、缩放、主题和屏幕阅读器人工检查？
- [ ] P0 / P1 缺陷已清零？
- [ ] 例外已经登记影响、替代路径、负责人和期限？
