# 前端应用架构规范

## 1. 适用范围

本规范定义 Web SPA 的公共应用架构：页面、业务能力、共享组件、基础设施与状态的职责边界，以及模块间允许的依赖方向。

- 技术基线与框架专属目录、路由约定由项目采用的技术 Profile 定义。
- 测试见《[[前端测试规范]]》。
- 交互与可访问性见《[[前端交互与可访问性规范]]》。

本规范不规定具体 Router、Store、组件库或文件扩展名。

## 2. 核心原则

### 2.1 Page 负责编排，Feature 负责业务能力

Page 对应一个可直接访问的路由页面，负责读取路由状态、组合多个业务能力并组织页面级反馈。

Feature 表达用户可以理解的业务能力，例如 auth、task、workspace、member、report。业务规则、业务组件、Query、Mutation、表单 Schema 与 Feature 私有状态优先留在对应 Feature。

禁止把业务规则长期堆积在 Page 中，也禁止为了“架构完整”把简单页面机械拆成大量空目录。

### 2.2 按业务能力组织，而不是按技术类型平铺

业务代码默认按 Feature 聚合。只有真正跨多个 Feature 的能力才进入共享目录。

禁止建立全局 `services/`、`models/`、`hooks/` 等大杂烩目录，把不同业务域的实现按技术类型打散。

### 2.3 状态只能有一个权威来源

同一份数据不得同时由 Router、服务端缓存、全局 Store 和组件 state 各保存一份可独立修改的副本。

默认归属顺序：

1. 可分享、可恢复的页面状态 → URL；
2. 服务端数据 → Query Cache；
3. 跨页面客户端状态 → Store；
4. 页面或组件短生命周期状态 → 本地状态。

### 2.4 依赖方向必须向下

高层负责组合低层；低层不得反向依赖业务页面或应用装配层。共享层不得读取某个 Feature 的 Store、Query 或 API。

### 2.5 先保持扁平，再按真实复杂度拆分

目录结构服务于理解和依赖边界，不以文件数量或行数作为拆分标准。只有出现独立职责、真实复用或明确边界时才增加子目录、Facade 或公共出口。

禁止预防性抽象。

## 3. 标准目录语义

```text
src/
├── app/          # 应用装配
├── pages/        # 路由页面
├── features/     # 业务能力
├── components/   # 跨 Feature 共享 UI / Layout
├── lib/          # 基础设施适配
├── utils/        # 通用纯函数
├── types/        # 真正跨 Feature 的公共类型
├── assets/
└── styles/
```

框架 Profile 可以补充 `hooks/`、`composables/`、`stores/` 等目录，但不得改变上述核心层级的语义和依赖方向。

### 3.1 `app/`：应用装配

`app/` 负责：

- 根组件；
- Router 安装；
- Query Client 与 Store 安装；
- 全局 Provider / Plugin；
- 全局错误边界；
- 应用级生命周期。

业务 Feature 不得 import `app/`。

### 3.2 `pages/`：路由页面

Page 可以：

- 读取路由参数、查询参数和导航状态；
- 调用 Feature 暴露的业务能力；
- 组合多个 Feature 与共享组件；
- 持有只服务当前页面的轻量 UI 状态。

Page 不得：

- 直接拼接 API URL 或调用裸 `fetch`；
- 定义需要跨页面复用的业务规则；
- 成为全局状态存储位置；
- 被 Feature、共享组件或 `lib/` 反向依赖。

### 3.3 `features/`：业务能力

Feature 内可以包含：

- 业务组件；
- Query 与 Mutation；
- 表单 Schema；
- Feature 私有状态逻辑；
- Feature 私有 Store；
- 业务类型与视图模型。

小 Feature 默认保持扁平。复杂度真实增加后，再拆 `components/`、`api/`、`schemas/` 等子目录。

Feature 之间允许少量明确的单向依赖，但不得形成循环。若两个 Feature 经常互相引用，优先：

1. 由 Page 在上层组合；
2. 把真正通用的 UI / 工具下沉；
3. 如果本质上属于同一业务能力，则合并 Feature。

### 3.4 `components/`：共享组件

`components/ui/` 保存没有业务语义的基础组件，`components/layout/` 保存跨页面布局。

只有至少两个 Feature 确实复用，或组件属于明确的设计系统基础设施时，才进入共享组件目录。

共享组件通过 props、children / slots、callback / emit 等公开契约工作，禁止直接读取具体 Feature 的 Store、Query 或 API。

### 3.5 `lib/`：基础设施适配

`lib/` 保存对浏览器或第三方基础设施的薄封装，例如：

- HTTP Client；
- API 生成物；
- Query Client 公共配置；
- 浏览器存储；
- 环境变量；
- 日志、日期和国际化适配。

`lib/` 不包含具体任务、订单、用户等业务判断，也不得 import `features/`、`pages/` 或 `app/`。

### 3.6 `utils/`、`types/`、`assets/` 与 `styles/`

- `utils/` 只保存无状态纯函数；
- `types/` 只保存真正跨 Feature 的公共类型；
- API DTO、组件 Props 与表单类型优先与所属模块共置；
- `assets/` 保存参与构建的静态资源；
- `styles/` 保存 Design Token、全局基础样式与主题入口。

## 4. 依赖规则

| 层 | 可以依赖 | 禁止依赖 |
| --- | --- | --- |
| `app` | 其他所有应用层 | 无下层限制 |
| `pages` | `features`、`components`、共享状态逻辑、`lib`、`utils` | `app` |
| `features` | `components`、共享状态逻辑、`lib`、`utils`、公共类型 | `pages`、`app` |
| `components` | 框架、样式、`utils`、通用类型 | `features`、`pages`、`app`、业务 API |
| 共享状态逻辑 | `lib`、`utils`、通用类型 | `pages`、具体业务 Feature |
| `lib` / `utils` | 第三方库与更底层文件 | `features`、`pages`、`app` |

### 4.1 Import 约定

- 同一小目录内使用相对路径；
- 跨层默认使用稳定的源码根别名；
- 禁止跨业务域使用多层 `../../../` 隐藏依赖关系；
- 不在每个目录机械创建 `index.ts`；
- Barrel 只用于稳定公共出口，不用于掩盖依赖；
- 禁止循环 import。

### 4.2 不强制 Feature 公共接口层

项目内部允许显式 import Feature 文件。只有导入路径频繁变化、Feature 被多个入口复用或确实需要限制公共 API 时，才增加稳定出口。

禁止为了形式解耦给每个 Feature 创建 Facade、事件总线或重复类型。

## 5. Router 与 URL

### 5.1 路由声明

路由表必须有集中、可审查的入口。公开 URL 不根据文件名隐式生成，除非项目明确采用另一套已记录的路由 Profile。

默认对 Page 做路由级代码分割；不为每个内部组件机械创建异步边界。

### 5.2 URL 是可分享页面状态的权威来源

以下状态默认进入 URL：

- 分页；
- 搜索词；
- 筛选与排序；
- 当前 Tab；
- 可直达的详情 ID。

以下状态默认留在本地：

- Dialog 的短暂开关；
- 未提交输入；
- Hover、Focus 与动画状态；
- 不需要刷新恢复的临时选择。

Page 负责把 Router 的字符串参数解析为明确类型后再传给 Feature。深层业务组件不得随意读取全局 Router。

### 5.3 路由守卫

守卫只处理进入页面前必须决定的导航问题，例如会话恢复、是否登录、访客访问和未保存修改。

普通业务数据由页面和 Feature Query 获取。前端守卫只改善体验，真正认证与授权必须由后端执行。

## 6. 状态归属

### 6.1 Server State

服务端返回的实体、列表、详情和权限集合默认由 Query Cache 管理。

Feature 负责 Query Key、Query Option、Mutation、失效策略和必要的乐观更新。组件不得自行维护第二份长期可变远端数据副本。

### 6.2 Client State

跨页面客户端状态只有在真实需要时才进入 Store。主题、导航偏好、跨页面草稿元数据可能符合条件。

Store 不因为已经安装就成为所有状态的默认位置。

### 6.3 页面状态保留

需要刷新、复制链接或前进后退恢复的状态优先进入 URL。只需组件生命周期内存在的状态留在局部。

## 7. API 与数据流

生产数据流默认遵循：

```text
Page
  ↓
Feature Query / Mutation
  ↓
Generated API / Feature API
  ↓
Unified HTTP Client
  ↓
HTTP
```

- Page 不直接调用裸 HTTP；
- 共享组件不调用业务 API；
- 生成代码不处理 Toast、导航或业务 Query Key；
- API DTO 与视图类型不必机械一一对应，必要转换留在 Feature 边界。

认证、refresh token 和 401 重放由选中的认证 Profile 定义。

## 8. 组件与 Feature 拆分

Page 保持为组合面。出现以下信号时再提取组件或 Feature：

- 独立业务能力；
- 多处真实复用；
- 独立测试价值；
- 独立生命周期或状态；
- 明确的公开输入输出契约。

禁止只因文件超过固定行数就拆分，也禁止抽象“以后可能复用”的组件。

## 9. 表单

- 表单 Schema 与业务规则放在所属 Feature；
- 简单表单使用框架原生能力；
- 复杂表单才引入框架 Profile 指定的表单库；
- 前端校验不能替代后端校验；
- 服务端字段错误必须映射回对应字段；
- 提交 Pending 时阻止重复业务操作。

## 10. Loading、Empty、Error 与 Success

页面和 Feature 必须明确处理适用的异步状态：

- Loading；
- Empty；
- Error；
- Success；
- Forbidden / Offline / Conflict（按场景）。

禁止只有“有数据”的快乐路径。状态的具体交互与可访问性要求见《[[前端交互与可访问性规范]]》。

## 11. 环境、配置与构建

- 环境变量只经统一校验入口读取；
- 浏览器端不得持有服务端 Secret；
- 构建配置保持集中；
- 生产构建输出视为不可变静态资源；
- 运行时配置需要变化时建立明确、可校验的入口。

## 12. 渐进式演进

小项目默认从较扁平的 Feature 结构开始。只有真实复杂度出现后增加子目录、Store、公共出口或抽象层。

典型提取信号包括：

- 同一能力开始有多个业务组件；
- Query / Mutation 明显增多；
- 多个页面共同消费同一业务能力；
- Feature 内出现可以清楚命名的子职责。

## 13. 禁止的反模式

- 按 `components/services/models` 全局平铺所有业务代码；
- Feature → Page 或共享层 → Feature 的反向依赖；
- Router、Store 与 Query Cache 保存同一远端数据副本；
- Page 直接调用裸 HTTP；
- 为每个 Feature 机械创建接口层与 Barrel；
- 全局 Event Bus 承担普通业务通信；
- 以“以后可能需要”为理由提前抽象。

## 14. 速查清单

- [ ] Page 只负责编排，没有沉积可复用业务规则。
- [ ] Feature 按业务能力组织。
- [ ] 共享组件不依赖具体 Feature。
- [ ] `lib/` 不依赖业务层。
- [ ] URL、Query Cache、Store、本地状态各有唯一职责。
- [ ] 没有循环 import。
- [ ] 新抽象由真实复杂度或复用驱动。
