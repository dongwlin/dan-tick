# Go 桌面应用架构约定

## 1. 适用范围

本 Profile 约定 Wails 3 单体桌面后端的 Go 代码组织、模型、数据访问与事务边界。以少量明确的业务包为默认方案，不要求传统 HTTP 服务端的 Handler / Service / Repository / Domain 四层结构。

## 2. 目录与依赖

- Go 应用根目录默认只放 `main.go`：负责嵌入前端资源、调用应用入口和报告启动失败；依赖装配、Wails Service 和业务实现放在 `internal/`。
- Wails 模板在 `build/` 下的生成或平台专属 Go 文件不属于应用根目录约束，不为遵守目录形式而迁移它们。
- 按实际业务能力分包，例如 `internal/app`、`internal/desktop`、`internal/task`、`internal/scheduler`、`internal/executor`、`internal/storage`；示例不是必须预建的目录清单。
- `app` 作为组合根，负责构造依赖和管理生命周期；其他包不得反向导入 `app`。Wails 入口层调用业务能力，业务逻辑不得依赖 Wails 窗口或 Binding。
- 包之间保持单向依赖，不形成循环导入。需要协调多个业务包时，由已有上层用例负责，不为协调而让底层包互相引用。
- 包名使用简短、全小写的职责名称；不建立没有明确职责的 `utils`、`common` 或预留的空包。文件按用途命名，同一包可以包含多个协作文件，不以固定行数为拆分标准。

## 3. 模型与对外类型

- Bun Model 默认允许直接用于业务代码；不强制为相同字段再复制一套 Domain Model、持久化模型和映射器。
- 当前端输入允许修改的字段与持久化字段不一致时，Wails 写入方法必须使用明确的 Input 类型，不直接接受包含 ID、内部状态或其他不可编辑字段的完整数据库模型。
- 查询返回类型仅在涉及敏感字段、计算或组合数据、序列化差异、公开契约独立演进等真实需求时与 Bun Model 分离。
- 对外暴露的 Go 类型和 JSON 字段属于 Binding 契约；新增数据库字段不能因此自动暴露秘密或不应公开的内部状态。
- Bun Tag、字段转换和必要的映射留在拥有这些数据的包内；只有存在实际边界差异时再抽取独立类型或转换函数。

## 4. SQL 与事务

- 简单 CRUD 允许业务包通过注入的 `*bun.DB` 执行；复杂或复用的查询可以抽为同包具体方法或文件，不强制全局 Repository 层及每表一套接口。
- `storage` 默认负责连接、SQLite 配置和迁移；不将所有业务 SQL 集中放进基础设施包。
- 跨多个数据库写入的业务用例由编排该用例的代码统一开启和提交事务。必要时使用 Bun `RunInTx` 与 `bun.IDB` 在同一事务中执行查询。
- 任务执行登记、防重和状态变更依赖 SQLite 约束与原子操作，不以进程内锁取代事务。
- 不把第三方 HTTP 请求、Cron 注册、Wails Event 等数据库之外的副作用放在事务中，并假设它们可以随 SQLite 一起回滚。提交后发生的副作用失败需要可报告、可重新同步的处理途径。

## 5. 错误与测试边界

- 业务可预期错误使用稳定类别，并通过 `errors.Is` / `errors.As` 判断；内部错误使用 `fmt.Errorf("%w", err)` 保留错误链，不根据错误消息文本做业务分支。
- Binding 层将错误转换为前端可识别且安全的结果；日志可保留必要的内部上下文，但不得记录敏感凭证。
- 默认依赖具体类型；仅在已有多个实现或需要替换真实外部边界（如时钟、HTTP、Keyring）时建立小接口。测试直接使用真实临时 SQLite，不为 Mock Bun 查询增加无意义的接口。
