# 后端数据模型设计

## 1. 范围与状态

本文记录 dan-tick MVP 的 **SQLite 逻辑模型**，依据 [PRD](PRD.md) 和 [技术栈选型](技术栈选型.md)。具体字段、SQL 约束、索引、事务、防重与迁移步骤统一参见 [SQLite Schema 与 Migration 设计](SQLite%20Schema%20与%20Migration%20设计.md)。六张业务表已在首个 Migration 中落地；对应的业务读写与调度尚未实现。

设计原则：Go / SQLite 是任务和执行历史的事实来源；任务定义、计划实例、每次发送结果分开保存；只为当前需求建立数据关系，不增加通用调度平台、多账号或全量事件溯源模型。

## 2. 实体关系

```text
rooms 1 ─── N tasks 1 ─── N task_messages
              │
              └────── N executions 1 ─── N send_attempts

app_settings                （非敏感应用配置）
系统 Keyring                （独立于 SQLite 的登录凭证）
```

没有独立的 `schedules` 表：MVP 每个任务仅有一套计划。计划定义和下一次待处理计划时刻放在 `tasks`；Cron 内存注册表可随时从数据库重建。

## 3. 建议的数据表

| 表 | 主要字段（示意） | 职责 |
| --- | --- | --- |
| `rooms` | `id`、`platform_room_id`、`title`、`anchor_name`、`remark`、`deleted_at` | 直播间及本地备注；平台房间 ID 唯一 |
| `tasks` | `id`、`room_id`、`name`、`kind`、`enabled`、`interval_seconds`、`max_count`、`max_duration_seconds`、`schedule_kind`、`timezone`、`local_date`、`local_time`、`weekdays`、`next_due_at`、`created_at`、`updated_at`、`deleted_at` | 任务定义、一次性/每日/每周规则和调度游标 |
| `task_messages` | `id`、`task_id`、`position`、`content` | 任务当前弹幕列表；按 `position, id` 排序 |
| `executions` | `id`、`task_id`、`trigger_kind`、`scheduled_at`、`status`、`created_at`、`queued_at`、`started_at`、`finished_at`、`sent_count`、`failed_count`、`error_code`、`error_message`、`task_name_snapshot`、`platform_room_id_snapshot` | 一次任务执行或错过的计划实例，保存列表和历史展示所需快照 |
| `send_attempts` | `id`、`execution_id`、`sequence`、`message_no`、`content_snapshot`、`attempted_at`、`result`、`error_code` | 单条消息的每次 HTTP 请求尝试，保留失败和有限重试轨迹 |
| `app_settings` | `key`、`value` | 语言、默认时区、调度总开关等普通配置，不保存 Cookie |

字段约定：

- 内部主键先采用 SQLite `INTEGER PRIMARY KEY`；B 站房间 ID 以规范化的外部标识存储，不与内部主键混用。
- `tasks.kind` 为单次发送或循环发送；`schedule_kind` 为一次性、每日或每周，两者互不替代。
- `timezone` 保存 IANA 时区（默认 `Asia/Shanghai`），`local_date` / `local_time` 保存用户输入的本地日历规则，`weekdays` 保存每周日期集合；它们不能因系统时区改变而重解释。
- `next_due_at` 是持久化的下一次**待处理**计划时刻，而非 Cron 注册 ID。编辑、禁用、恢复或处理计划实例时由业务事务维护；无下一次运行时允许为空。
- `scheduled_at`、`next_due_at` 和各执行时间采用 UTC Unix 毫秒整数；本地日期 / 时间只用于描述日历规则，不与 UTC 时刻混用。
- `trigger_kind` 区分计划执行和手动执行。手动执行的 `scheduled_at` 为空，不消耗定时计划；`status` 区分排队、运行、完成、失败、停止、错过及异常中断等业务状态。启用状态只存在于 `tasks.enabled`。
- 历史需要在任务修改后仍可识别当时名称、直播间与发送内容，因此执行与尝试中保留必要快照；避免为此复制所有任务字段。

## 4. 关键约束和索引

- `rooms.platform_room_id` 建唯一约束，`tasks.room_id`、`task_messages.task_id`、`executions.task_id`、`send_attempts.execution_id` 建外键并启用 SQLite 外键检查。
- **自动计划去重**：`executions` 对 `(task_id, scheduled_at)` 建仅适用于 `trigger_kind = 'scheduled'` 的唯一索引；另对同一任务的活跃执行建立部分唯一索引，防止不同计划或手动执行彼此重叠。登记与推进调度游标须属于同一个事务。
- `task_messages` 使用 `(task_id, position, id)` 辅助排序；不为调整顺序强制采用易产生中间冲突的 `(task_id, position)` 唯一约束。
- 常用查询索引优先覆盖直播间下的任务、待处理计划、任务 / 全局执行历史和活跃执行；索引的具体定义以 Schema 文档为准，不预置大量索引。
- 对于直播间、任务删除，MVP 默认采用**逻辑删除**并取消未来调度，保留执行历史所引用的实体。删除直播间时应明确告知其关联任务也会被禁用和逻辑删除；历史记录清理与最终物理删除独立处理。
- 重新添加已逻辑删除的相同 B 站房间 ID 时，优先恢复原记录而不是插入另一条冲突的房间记录。

## 5. 数据一致性与恢复

1. 保存任务：在 SQLite 事务中保存任务、弹幕列表和 `next_due_at`；提交后刷新 Cron 注册，并发送 Wails Event。Cron 更新失败时显式报错并允许从数据库重新同步，不能声称数据库提交已回滚。
2. 定时触发：使用计划时刻而非回调实际时钟值建立执行标识。一个事务内检查有效性、唯一登记 `executions`、推进 `next_due_at`；事务提交后才交给执行器。
3. 错过计划：系统睡眠或应用重新启动后，根据持久化 `next_due_at` 和当前时刻判断过期计划，记录 `missed` 并推进游标；不为历史计划补发弹幕，也不无上限追溯生成执行批次。
4. 执行结果：请求发送前持久化 `pending` 尝试，结束后更新尝试结果与执行计数；异常中断的 `pending` 结果视为未知，不自动重试。停止、失败或异常退出都应落在明确的最终状态，不恢复循环发送进度。
5. 历史保留：默认清理 30 天以前的执行和尝试记录；业务执行记录不等于 zerolog 诊断日志，清理时不触碰任务定义及 Keyring。

## 6. 实现时仍需验证的细节

- **调度时间语义**：迟到宽限窗口的具体数值仍待调度实现时确定；夏令时重复 / 不存在时间和离线错过记录的处理策略已写入 Schema 文档，需要用实际 Cron 计算验证。
- **迁移与时间编码**：通过真实 SQLite 验证 `STRICT` 表、UTC 毫秒往返、唯一索引、事务失败回滚与迁移版本记录。
- **执行过程**：验证未确认的请求和崩溃恢复不会造成自动重发；明确错误信息脱敏边界。
- **删除与清理**：验证逻辑删除后历史筛选和 30 天清理行为；避免残留无法关联的历史。

这些属于后续实现决策，不提前新增无依据的表、列、接口或抽象层。
