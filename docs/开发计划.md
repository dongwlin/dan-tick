# dan-tick 开发计划

## 1. 范围与执行原则

本文安排 **P0 最小可用桌面应用** 的实施顺序，并列出可独立提交的最小工作单元。功能边界及验收标准以 [PRD](PRD.md) 为准；技术方案以 [技术栈选型](技术栈选型.md) 为准。数据库及外部接口分别参考 [SQLite Schema 与 Migration 设计](SQLite%20Schema%20与%20Migration%20设计.md) 和 [B 站 API 对接参考](B%20站%20API%20对接参考.md)。本计划不是对这些文档的重复定义。

**当前进度（2026-10-11）：** A1 已确定 Go module，A2 已完成 SQLite 建库与首次 Migration，A3 已实现独立的计划下一时刻计算及日历边界测试；B1 已实现直播间输入解析、真实房间号查询与可选展示信息获取，B2 已实现直播间持久化管理、恢复及关联任务逻辑删除，B3 已实现任务创建与有序消息的事务持久化和读取，B4 已实现任务编辑、启用 / 禁用及逻辑删除；C1 已接入系统 Keyring 凭证读写与错误反馈，目标平台实机核对待后续账号入口接入后执行；C2 已实现从 Keyring 读取凭证并通过 B 站 `nav` 接口检测登录状态；C3 已实现单次直播弹幕发送 HTTP 客户端及安全结果分类；C4 已实现单账号共享限流和走同一入口的测试发送；L1 已实现持久化、轮转及安全诊断日志并接入启动 / 数据库故障 / 退出流程；D1～D3 已完成手动执行、循环与停止、逐条尝试持久化、账号级 FIFO 排队与冲突处理；E1 已实现事务化计划领取及冲突记录，E2 已实现 Cron 注册、变更同步及已领取计划实例的执行入口，E3 已实现启动 / 唤醒恢复与迟到错过判定，E4 已实现执行历史查询，E5 已实现 30 天自动清理，E6 已实现非敏感设置持久化与调度总开关，L2 已覆盖执行、调度和恢复的安全事件；FE1～FE6 已完成构建、静态检查、Hash 路由、视觉主题、交互原语与行为测试，F3 已完成正式 Vue 侧栏、自绘标题栏和窗口框架。**F1 已完成共享 Sender / Executor / Scheduler 的生命周期装配和直播间 / 任务 Wails Binding；正式业务页面尚未迁移。** `prototype/` 六类页面已确认定稿，设计基线为 commit `4bb1188`；这不代表真实业务页面已经完成。下列单元以勾选状态记录完成情况，不因只有设计文档或原型就标记完成。

- **先形成可靠业务内核，再迁移正式 UI。** UI 原型已定稿，可以作为 F 阶段的统一设计依据；Go 数据、调度、凭证和发送能力仍按各自计划实施。正式 Vue 页面保留原型的视觉与交互要求，但不直接复用原型的 Vanilla TypeScript 业务状态。
- **以行为作为提交单位，不以目录或层次作为提交单位。** 一个单元必须有实际可调用的能力、明确的测试或人工验收方式；不提交只有接口、空包、占位组件或未使用依赖的“准备工作”。必要的实现与其测试一起提交。
- **每次提交保持基线可用。** Go 代码可通过受影响的测试；涉及 Wails / Binding / 正式前端时要能重新生成 Binding 并构建桌面应用。涉及 SQLite Schema 的最初版本作为一组完整迁移提交；后续已发布迁移只追加、不改写。
- **按风险拆分，不机械地一行一 Commit。** 以下每个编号是建议的最小可提交单元；如果实现时一个单元出现两个能够分别完成验收的行为，可以继续拆分。如果无法独立验证，合并相关小步，不制造半成品提交。
- **所有自动测试不得访问真实 B 站或使用真实 Cookie。** 通过 `httptest`、临时 SQLite、可控时间及必要的外部能力替身验证；真实账号发送仅在用户明确安排的人工验收中进行，并遵守平台限制。

### B. 直播间和任务配置

| 单元 | 本次只做什么 | 可提交条件 |
| --- | --- | --- |
| [x] B1 | 用 Go `net/http` 解析直播间 ID / 链接、查询并规范化真实房间 ID，按需获取标题和主播信息 | `httptest` 覆盖有效短号、接口拒绝、超时和返回字段缺失；不需要用户登录 |
| [x] B2 | 实现直播间列表、添加、备注修改、逻辑删除及重复添加后的恢复 | 真实 SQLite 测试验证唯一房间 ID、恢复及删除时关联任务的禁用和逻辑删除；房间展示信息查询失败不误停调度 |
| [x] B3 | 实现任务创建与读取，保存有序消息列表并计算 `next_due_at` | 真实 SQLite 事务测试验证合法性、提交和回滚、重启后任务和消息仍在 |
| [x] B4 | 实现任务编辑、启用 / 禁用、逻辑删除；与关联直播间的有效性保持一致 | 真实 SQLite 测试验证编辑失败回滚、禁用后无有效待执行计划、删除后历史关联不丢失 |

B2 当前采用安全边界：若直播间关联任务仍存在 `waiting` / `queued` / `running` 执行，删除会返回冲突且整个事务回滚；待执行器停止能力落地后，由上层先停止活跃执行再删除，不能直接把未停止的执行标为终态。恢复已删除直播间不会自动恢复已删除任务。

B3 任务创建校验单次 / 循环类型、非空消息、循环停止条件及计划规则；空消息会过滤，启用计划通过 A3 计算下次执行时刻并保存 UTC 毫秒，禁用任务不保留有效执行游标。平台实际允许的弹幕长度和最短发送间隔仍需在 C3 / C4 对接真实发送规则时核实，当前不会声称已通过 B 站生产接口验证。

B4 编辑任务时会重新校验直播间有效性和完整配置；仅更改名称、内容或直播间而未更改计划时保留已持久化的 `next_due_at`，更改计划或重新启用时才计算未来时刻。禁用任务只清理后续调度，不会假装取消正在进行的执行；编辑或删除仍有 `waiting` / `queued` / `running` 执行的任务会返回冲突，需在后续执行器支持停止后先处理执行，再重试操作。任务逻辑删除保留消息及执行历史关联。

### C. 凭证与发送通道

| 单元 | 本次只做什么 | 可提交条件 |
| --- | --- | --- |
| [x] C1 | 接入系统 Keyring 的写入、更新、清除和读取能力，并定义不可用时的错误反馈 | 使用替代的安全存储边界测试增删及失败；实际 Linux Secret Service / Windows Credential Manager 分别安排手动核对，绝不回退明文 |
| [x] C2 | 接入 B 站登录状态检测（读取 Keyring 凭证），返回可供界面使用的非敏感状态 | `httptest` 覆盖有效、失效、接口错误；日志、返回值均不得泄漏 Cookie |
| [x] C3 | 实现直播弹幕 HTTP 客户端，统一请求构造、超时、取消、业务响应判定与安全错误分类 | `httptest` 覆盖成功、鉴权失败、限流、超时及结果未知；HTTP 200 不等于成功，不确定结果不自动重发 |
| [x] C4 | 实现单账号共享发送限流入口，并使“测试发送”通过同一入口完成一次请求 | 模拟连续请求证明限流、取消和错误传播；测试发送返回真实客户端结果，不新建任务执行记录 |

C1 使用 `github.com/zalando/go-keyring`，在 `dan-tick` 服务下以单个 `bilibili` 项保存 `SESSDATA` 与 `bili_jct`，更新时整体替换；未配置、输入不合法、存储值损坏与系统安全存储不可用均有独立错误类别，错误反馈不包含底层可能携带的凭证内容。读写仅供 Go 后端使用，不进入 SQLite、日志或普通前端状态，也不会降级为明文文件。

**C1 平台手工核对（待 F2 接入正式账号入口后执行，当前尚未完成）：** 在 Linux 的带有可解锁 `login` 集合的 Secret Service 会话、Windows 的 Credential Manager 中，分别用虚构测试凭证验证首次保存、关闭重启后读取、覆盖更新、清除与再次读取；并在 Linux 缺失 / 锁定 Secret Service、Windows 安全存储无法访问的情况下确认显示不可用错误且不创建明文配置。人工核对不使用真实账号 Cookie，不将测试值写入项目文件；自动单元测试不访问操作系统 Keyring。

C2 在 `internal/account` 中提供 Go 后端登录检查：从 C1 Keyring 存储读取凭证，以仅含 `SESSDATA` 的 Cookie 请求 `GET /x/web-interface/nav`，仅当 `code = 0` 且 `data.isLogin = true` 时判定已登录；`code = -101` 或成功响应中的 `isLogin = false` 判定过期，其余响应错误不误判为过期。对外只返回 `unconfigured`、`logged_in`、`expired`、`verification_failed` 非敏感最终状态，`checking` 留给 F5 界面请求期间表示；HTTP 请求有超时及取消、禁止携 Cookie 重定向、不读取客户端 Cookie Jar，底层 HTTP 错误及 B 站响应文本均不回显。`httptest` 已覆盖主要分支；实际账号检测和界面呈现仍待后续人工验收与 F2 / F5 集成，不以本单元测试代替。

C3 在 `internal/danmaku` 中提供 `Client.Send(ctx, roomID, message)`，按次从 C1 Keyring 读取凭证，只接受规范化的房间号与非空合法文本，构造包含 `roomid`、`msg`、秒级 `rnd`、`fontsize`、`color`、`csrf` 的表单及 `SESSDATA` / `bili_jct` Cookie。只在 HTTP 200 且业务 `code = 0` 时记录 `accepted`；已知拒绝码返回 `rejected` 及安全错误分类；无法确认是否成功的网络 / HTTP / 响应异常返回 `unknown`，请求前失败返回 `not_sent`。所有发送只尝试一次，取消和超时均不得自行补发；不跟随重定向、不带客户端 Cookie Jar，不回显原始响应、请求或敏感错误。测试仅使用假 Keyring 和 `httptest`；平台允许的实际长度、间隔和发送行为仍需独立人工核对。单账号共享限流及测试发送入口留给 C4，执行记录留给 D 阶段，Wails Binding 留给 F 阶段。

C4 在同一 `internal/danmaku` 包中提供长期复用的 `Sender`：`Send` 与 `TestSend` 共用一个账号级串行发送许可，在上一次已发请求返回后等待至少 15 秒，保守保证实际 HTTP 请求间隔不会被 Keyring 读取或请求耗时压缩；`unknown` 和明确拒绝都计入间隔，`not_sent` 和等待期间取消不消耗发送机会。当前 15 秒只是 PRD 建议的保守默认值，**未经真实平台规则确认，并非官方最低间隔**；对 `ErrRateLimited` 原样传播，让调用方停止或暂停该次执行，不尝试规避限流。测试发送直接返回 C3 HTTP 客户端的结果，不触碰 SQLite、任务实例或执行记录。D 阶段的执行器与 F 阶段的 Binding 必须共同复用**同一个** `Sender` 实例，不得另建限流器绕过账号级约束；严格的执行队列顺序与冲突处理仍属于 D3，真实账号发送验收需单独授权。

### L. 应用诊断日志

诊断日志使用既定的 `zerolog`，与 SQLite 任务执行历史分离。默认开启、写入用户级日志目录，不依赖控制台或数据库可用性。建议初始默认值：`info` 级别、JSON Lines、单文件最大 10 MiB、最多 5 个文件（含当前文件）、最多保留 14 天；具体轮转策略实施时需验证跨平台行为和总磁盘上限。

| --- | --- | --- |
| [x] L1 | 初始化统一 Logger 并在数据库打开前接入应用启动 / 退出 / 致命错误；持久化写入、文件轮转和过期清理；定义安全字段与写入失败降级策略 | 临时目录测试覆盖正常写入、重启可读、并发写入、轮转及保留上限、日志目录不可写；不因日志故障阻断核心业务，且有可观察的降级提示；敏感值不落盘 |

**E6 实施记录：** `internal/settings.Service` 使用已有 SQLite `app_settings` 键值表保存普通设置，不增加 Migration、不保存 Keyring 凭证；缺少键时默认 `default_timezone=Asia/Shanghai` 和 `scheduling_enabled=true`，写入时验证 IANA 时区、拒绝 `Local`，持久化总开关仅使用 `true/false`。`task.Service.Create` 在未指定时区时读取当前默认值，`Update` 不指定时区则保留任务原时区；设置改变不重解释既有任务的计划时间。**运行中的总开关必须通过 `scheduler.Manager.SetSchedulingEnabled(ctx, enabled)` 修改**，以保证持久化后同步 Cron；暂停撤销所有未来 Cron 注册、不改动逐任务 `enabled`、`next_due_at` 或已有历史，也不取消已经交接的执行。调度启动、重建、任务变更遵守持久化开关，计划领取与迟到回调在同一 SQLite 事务内再次检查开关，避免已暂停后旧回调创建新执行。重新启用时先以 E3 的唤醒恢复规则将过期计划记为 `missed` 并推进游标，再注册未来唤醒，**不补发**；启动时无论开关状态仍要收尾遗留活跃执行。偏好提交成功但恢复 / 注册失败时返回错误，可由 `Resume` 重试同步，不伪称数据库回滚。真实 SQLite 测试覆盖重启、默认时区对新旧任务的作用、暂停后不领取、重建 / 修改不重注册、恢复不补发、历史保留、非法设置与写入失败。**正式设置页和 Binding 留待 F 阶段接入，当前生产入口仍未启用自动调度。**

## 4. 单元如何执行与提交

执行任一编号时，先读其引用的需求与设计，仅实现该编号所需的真实行为。完成后：

1. **验证本单元**：纯规则跑对应 Go 测试；数据库用真实临时 SQLite（恢复场景重新打开）；第三方 HTTP 用 `httptest`；UI 原型修改在 `prototype/` 跑 `pnpm build`，正式 Vue 修改在 `frontend/` 跑 `pnpm run test`、`pnpm run lint`、`pnpm run format:check` 和包含类型检查的 `pnpm run build`。必要时再运行 Wails 桌面构建与平台手工验收。
2. **确认集成边界**：修改 Go 后酌情执行 `go test ./...`、`go vet ./...`；并发相关代码按环境执行 `go test -race ./...`。独立 Go 命令执行前需有 `frontend/dist/` 供 `go:embed` 使用；正式前端构建前需生成 Wails Binding。不能运行的检查记录具体原因，不视为通过。
3. **仅提交本单元**：执行 `git diff --check`、`git status --short`，检查未混入生成目录、Cookie 或他人改动；按项目约定用英文 Conventional Commit，例如 `feat(storage): add initial sqlite migrations` 或 `feat(task): persist task changes`。若单元间有不可拆的共同改动，合为一个清楚的 Commit 并说明原因，不留必须靠下一提交才能修复的中间状态。
4. **更新进度**：可勾选上表已通过验收的单元；当需求或依赖改变时更新相关条目及验收条件，而不是把计划当作不可调整的固定承诺。未完成前不要勾选。
