# dan-tick 开发计划

## 1. 范围与执行原则

本文安排 **P0 最小可用桌面应用** 的实施顺序，并列出可独立提交的最小工作单元。功能边界及验收标准以 [PRD](PRD.md) 为准；技术方案以 [技术栈选型](技术栈选型.md) 为准。数据库及外部接口分别参考 [SQLite Schema 与 Migration 设计](SQLite%20Schema%20与%20Migration%20设计.md) 和 [B 站 API 对接参考](B%20站%20API%20对接参考.md)。本计划不是对这些文档的重复定义。

**当前进度（2026-10-11）：** A1 已确定 Go module，A2 已完成 SQLite 建库与首次 Migration，A3 已实现独立的计划下一时刻计算及日历边界测试；B1 已实现直播间输入解析、真实房间号查询与可选展示信息获取，B2 已实现直播间持久化管理、恢复及关联任务逻辑删除，B3 已实现任务创建与有序消息的事务持久化和读取。正式 `frontend/` 和 Wails Service 仍以模板为主，任务编辑、Cron 注册与发送功能尚未实现。`prototype/` 是使用演示数据的独立 UI 原型，仍会继续调整。下列单元以勾选状态记录完成情况，不因只有设计文档或原型就标记完成。

- **先形成可靠业务内核，再迁移正式 UI。** 原型可继续独立迭代；Go 数据、调度、凭证和发送能力不以原型视觉定稿为前置条件。正式 Vue 页面的交互迁移在对应设计稳定后进行，不直接复用原型的 Vanilla TypeScript 业务状态。
- **以行为作为提交单位，不以目录或层次作为提交单位。** 一个单元必须有实际可调用的能力、明确的测试或人工验收方式；不提交只有接口、空包、占位组件或未使用依赖的“准备工作”。必要的实现与其测试一起提交。
- **每次提交保持基线可用。** Go 代码可通过受影响的测试；涉及 Wails / Binding / 正式前端时要能重新生成 Binding 并构建桌面应用。涉及 SQLite Schema 的最初版本作为一组完整迁移提交；后续已发布迁移只追加、不改写。
- **按风险拆分，不机械地一行一 Commit。** 以下每个编号是建议的最小可提交单元；如果实现时一个单元出现两个能够分别完成验收的行为，可以继续拆分。如果无法独立验证，合并相关小步，不制造半成品提交。
- **所有自动测试不得访问真实 B 站或使用真实 Cookie。** 通过 `httptest`、临时 SQLite、可控时间及必要的外部能力替身验证；真实账号发送仅在用户明确安排的人工验收中进行，并遵守平台限制。

## 2. 开发顺序总览

| 阶段 | 交付目标 | 前置依赖 | UI 原型的关系 |
| --- | --- | --- | --- |
| A. 工程与数据基础 | 可构建的项目入口、数据库迁移、计划时间计算 | 当前模板 | 无依赖 |
| B. 任务配置 | 直播间解析与持久化、任务增删改查 | A | 无依赖 |
| C. 账号与发送 | 安全凭证、登录检测、可控的真实接口调用 | A；部分依赖 B | 无依赖 |
| D. 手动执行 | 单次 / 循环执行、发送记录、停止与统一限流 | B、C | 无依赖 |
| E. 自动调度与恢复 | 防重登记、Cron、错过计划、崩溃恢复 | B、D | 无依赖 |
| F. 正式前端集成 | Binding、Events、Vue 页面与业务联通 | 对应 Go 用例可用 | **对应页面设计稳定后**再迁移 |
| G. 桌面验收 | 后台生命周期、单实例、平台行为和交付核验 | E、F 的关键路径 | 不等待非关键视觉细节 |

推荐按表中顺序推进；**B 与 C 中相互独立的部分可以穿插**，F 中的 Binding 也可在对应 Go 用例稳定后提前接入，以尽早发现 Wails 集成问题。不要为了等待 UI 设计而停下 A～E，也不要求原型在某个日期整体冻结。

## 3. 最小可执行、可提交单元

下表每个编号均以“代码或文档变更 + 同次必要验证”为一组；方框仅用于后续记录完成情况。阶段验收只检查实质行为，不以已建立目录、已安装依赖或已有截图充当完成。

### A. 工程与数据基础

| 单元 | 本次只做什么 | 可提交条件 |
| --- | --- | --- |
| [x] A1 | 确定正式 Go module 名称，更新原有导入及 Wails Binding 生成路径；保持当前模板能运行 | `wails3 build` 成功，生成的 Binding 导入正确；不顺手创建业务空包 |
| [x] A2 | 接入 Bun + `modernc.org/sqlite`，实现数据库打开、关闭、首次迁移和重复启动；首个 Migration 一次性建立既定六张业务表与索引 | 临时 SQLite 测试覆盖迁移、重新打开、外键和失败回滚；应用启动失败不覆盖用户数据 |
| [x] A3 | 实现一次性 / 每日 / 每周计划的下一时刻计算（含时区），供任务保存和调度共享 | 可控时间测试覆盖普通日期、跨日、夏令时不存在 / 重复时间；不引入轮询调度 |

### B. 直播间和任务配置

| 单元 | 本次只做什么 | 可提交条件 |
| --- | --- | --- |
| [x] B1 | 用 Go `net/http` 解析直播间 ID / 链接、查询并规范化真实房间 ID，按需获取标题和主播信息 | `httptest` 覆盖有效短号、接口拒绝、超时和返回字段缺失；不需要用户登录 |
| [x] B2 | 实现直播间列表、添加、备注修改、逻辑删除及重复添加后的恢复 | 真实 SQLite 测试验证唯一房间 ID、恢复及删除时关联任务的禁用和逻辑删除；房间展示信息查询失败不误停调度 |
| [x] B3 | 实现任务创建与读取，保存有序消息列表并计算 `next_due_at` | 真实 SQLite 事务测试验证合法性、提交和回滚、重启后任务和消息仍在 |
| [ ] B4 | 实现任务编辑、启用 / 禁用、逻辑删除；与关联直播间的有效性保持一致 | 真实 SQLite 测试验证编辑失败回滚、禁用后无有效待执行计划、删除后历史关联不丢失 |

B2 当前采用安全边界：若直播间关联任务仍存在 `waiting` / `queued` / `running` 执行，删除会返回冲突且整个事务回滚；待执行器停止能力落地后，由上层先停止活跃执行再删除，不能直接把未停止的执行标为终态。恢复已删除直播间不会自动恢复已删除任务。

B3 任务创建校验单次 / 循环类型、非空消息、循环停止条件及计划规则；空消息会过滤，启用计划通过 A3 计算下次执行时刻并保存 UTC 毫秒，禁用任务不保留有效执行游标。平台实际允许的弹幕长度和最短发送间隔仍需在 C3 / C4 对接真实发送规则时核实，当前不会声称已通过 B 站生产接口验证。

### C. 凭证与发送通道

| 单元 | 本次只做什么 | 可提交条件 |
| --- | --- | --- |
| [ ] C1 | 接入系统 Keyring 的写入、更新、清除和读取能力，并定义不可用时的错误反馈 | 使用替代的安全存储边界测试增删及失败；实际 Linux Secret Service / Windows Credential Manager 分别安排手动核对，绝不回退明文 |
| [ ] C2 | 接入 B 站登录状态检测（读取 Keyring 凭证），返回可供界面使用的非敏感状态 | `httptest` 覆盖有效、失效、接口错误；日志、返回值均不得泄漏 Cookie |
| [ ] C3 | 实现直播弹幕 HTTP 客户端，统一请求构造、超时、取消、业务响应判定与安全错误分类 | `httptest` 覆盖成功、鉴权失败、限流、超时及结果未知；HTTP 200 不等于成功，不确定结果不自动重发 |
| [ ] C4 | 实现单账号共享发送限流入口，并使“测试发送”通过同一入口完成一次请求 | 模拟连续请求证明限流、取消和错误传播；测试发送返回真实客户端结果，不新建任务执行记录 |

### E. 自动调度与恢复

| 单元 | 本次只做什么 | 可提交条件 |
| --- | --- | --- |
| [ ] E1 | 在 SQLite 事务中按 `task_id + scheduled_at` 原子领取计划、登记 `scheduled` 执行并推进 `next_due_at` | 同一计划重复触发只登记一次；同时运行冲突写为 `missed`；失败事务不产生半个执行实例 |

| [ ] E3 | 完成启动 / 睡眠恢复核对：错过判定、过期游标推进、遗留执行和 `pending` 结果收尾 | 先确定迟到宽限阈值并写入测试；关闭后重新打开 SQLite 验证不补发、不重复执行、不无限追溯历史，恢复后无虚假的运行中状态 |

| [ ] E6 | 实现 P0 非敏感设置（如默认时区、调度总开关）的保存及恢复 | 重启后设置仍有效，暂停自动调度不会清除任务或影响已有历史；Keyring 不进入普通设置 |

| [ ] F1 | 将直播间 / 任务管理用例接入 Wails Service Binding，使用明确的写入 Input 和安全返回值 | 自动生成 TS Binding 后正式前端可构建；Go 输入校验仍权威；不添加本地 HTTP API |

| [ ] F4 | 接入直播间和任务列表 / 编辑页面，逐步加入实际需要的 Query、表单和组件 | 通过真实 Binding 完成新增 / 修改 / 禁用，并能在重开窗口后读取持久化结果 |

## 4. 单元如何执行与提交

执行任一编号时，先读其引用的需求与设计，仅实现该编号所需的真实行为。完成后：

1. **验证本单元**：纯规则跑对应 Go 测试；数据库用真实临时 SQLite（恢复场景重新打开）；第三方 HTTP 用 `httptest`；UI 原型修改在 `prototype/` 跑 `pnpm build`，正式 Vue 修改在 `frontend/` 跑 `npm run build`。必要时再运行 Wails 桌面构建与平台手工验收。
2. **确认集成边界**：修改 Go 后酌情执行 `go test ./...`、`go vet ./...`；并发相关代码按环境执行 `go test -race ./...`。独立 Go 命令执行前需有 `frontend/dist/` 供 `go:embed` 使用；正式前端构建前需生成 Wails Binding。不能运行的检查记录具体原因，不视为通过。
3. **仅提交本单元**：执行 `git diff --check`、`git status --short`，检查未混入生成目录、Cookie 或他人改动；按项目约定用英文 Conventional Commit，例如 `feat(storage): add initial sqlite migrations` 或 `feat(task): persist task changes`。若单元间有不可拆的共同改动，合为一个清楚的 Commit 并说明原因，不留必须靠下一提交才能修复的中间状态。
4. **更新进度**：可勾选上表已通过验收的单元；当需求或依赖改变时更新相关条目及验收条件，而不是把计划当作不可调整的固定承诺。未完成前不要勾选。

**建议从 A1 开始。** 但原型可以继续按 [原型说明](../prototype/README.md) 独立优化；本计划不要求先停止原型迭代，也不要求先撰写完整的 UI 交互规范才开始 Go 开发。
