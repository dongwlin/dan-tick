# B 站直播弹幕定时发送工具 — 产品需求文档

- 文档版本：v1.0
- 项目阶段：MVP（第一版）
- 应用类型：跨平台桌面应用
- 桌面应用框架：Wails 3
- 后端语言：Go
- 前端技术方案：已确定，见 [技术栈选型](技术栈选型.md)（尚未完成业务接入）
- 目标平台：Windows、Linux
- 数据存储：本地
- 核心定位：轻量、可靠、可无人值守的 B 站直播弹幕自动发送工具

---

## 1. 项目概述

### 1.1 项目背景

B 站直播间中的弹幕发送需要用户手动进入直播间并进行操作。

对于需要在固定时间发送弹幕、重复发送预设内容或执行周期性弹幕任务的场景，手动操作较为繁琐。

现有的独轮车工具主要通过浏览器脚本实现，通常依赖直播间页面保持打开，且部分工具缺乏完整的定时任务管理能力。

本项目计划开发一款基于 Wails 3 的跨平台桌面应用，通过 Go 后端直接调用 B 站直播弹幕接口，实现弹幕任务的配置、调度、发送和管理。

### 1.2 项目目标

第一版需要实现以下目标：

1. 无需打开浏览器或直播间网页即可发送弹幕。
2. 支持设置指定时间自动执行弹幕任务。
3. 支持周期性任务和单次任务。
4. 支持单条弹幕发送和多条弹幕循环发送。
5. 支持管理多个直播间和多个独立任务。
6. 支持应用在后台持续运行。
7. 支持 Windows 和 Linux 平台。
8. 支持持久化保存任务及执行状态。
9. 支持查看任务执行记录和错误原因。
10. 提供简单、直观的图形操作界面。

### 1.3 设计原则

- 本地优先：核心功能在本地完成，不依赖自建云服务。
- 轻量运行：尽量降低内存和 CPU 占用。
- 无浏览器依赖：弹幕发送通过 HTTP 接口完成。
- 跨平台一致：Windows 和 Linux 具有相同的核心功能。
- 稳定可靠：避免漏发、重复发送和任务状态异常。
- 安全存储：妥善保护用户的 B 站登录凭证。
- 易于维护：模块职责清晰，便于未来增加功能。
- 克制设计：第一版不引入没有明确价值的复杂功能。

## 2. 目标用户与使用场景

### 2.1 目标用户

主要面向需要管理 B 站直播弹幕发送任务的个人用户。

应用按照单用户、本地运行的方式设计。

暂不考虑多用户协作、远程服务端或商业化场景。

### 2.2 核心使用场景

#### 场景 A：每天定时发送一条弹幕

用户希望每天晚上 22:00 向指定 B 站直播间发送：

“晚上好”

用户操作：

1. 添加目标直播间。
2. 创建定时任务。
3. 设置执行时间为每天 22:00。
4. 输入弹幕内容。
5. 启用任务。

预期结果：

应用在每天 22:00 自动向对应直播间发送弹幕。

整个过程不需要打开浏览器或手动进入直播间。

#### 场景 B：定时启动独轮车

用户希望每天晚上 22:00 开始发送预设弹幕。

预设内容：

- 第一条弹幕
- 第二条弹幕
- 第三条弹幕

发送间隔为 15 秒，持续运行 5 分钟。

预期结果：

1. 22:00 自动启动任务。
2. 按顺序发送预设弹幕。
3. 发送到队列末尾后重新从第一条开始。
4. 每次发送之间保持指定间隔。
5. 达到 5 分钟后自动停止。
6. 记录任务执行结果。

#### 场景 C：立即执行

用户希望不等待定时任务，直接发送一条弹幕或启动已有任务。

预期结果：

用户点击“立即执行”后，程序立即开始发送，无需修改原定时任务。

#### 场景 D：后台运行

用户希望设置好任务后关闭主窗口，继续进行其他工作。

预期结果：

应用可以在后台保持运行，并按计划执行任务。

#### 场景 E：跨平台使用

用户可能在 Windows 或 Linux 上运行应用。

预期结果：

两个平台使用一致的配置格式、任务逻辑和操作流程。

## 3. 功能需求

### 3.1 B 站账号管理

#### FR-001：账号凭证配置

应用需要支持配置 B 站账号的登录凭证。

第一版至少支持通过用户手动输入或导入必要 Cookie 的方式进行配置。

必要凭证包括：

- SESSDATA
- bili_jct

具体需要的字段应以实际接口要求为准。

要求：

1. 提供独立的账号设置入口。
2. 用户能够添加、更新和清除登录凭证。
3. 用户能够测试当前凭证是否有效。
4. 不要求用户每次启动应用时重新输入。
5. 不允许在日志中输出完整 Cookie。
6. 不允许将凭证明文保存在普通配置文件中。

账号数量：

第一版仅要求支持一个 B 站账号。

多账号管理不属于第一版范围。

#### FR-002：登录状态检测

应用需要能够检测账号是否处于有效登录状态。

状态包括：

- 未配置
- 验证中
- 已登录
- 已过期
- 验证失败

账号验证成功后，设置页应在凭证卡片上方展示头像、昵称和 UID；侧栏底部仅显示账号头像。头像不可用时回退默认用户图标，未登录或验证失败时不展示历史账号资料。账号资料来自后端的登录检查结果，不包含 Cookie。

当登录凭证失效时：

1. 不再执行需要有效凭证的发送任务。
2. 将对应任务标记为失败。
3. 提示用户重新配置登录凭证。
4. 不进行无限重试。
5. 不自动清除用户的任务配置。

#### FR-003：凭证安全

登录凭证属于敏感信息，必须采取必要的安全措施。

要求：

1. 优先使用操作系统提供的安全凭证存储能力。
2. Windows 优先使用系统凭证管理能力。
3. Linux 优先使用 Secret Service 等安全存储机制。
4. 不支持安全存储时应明确提示，不得悄悄降级为明文存储。
5. 前端页面不应长期持有完整凭证。
6. 所有需要身份验证的请求由 Go 后端完成。
7. 用户可以主动清除保存的凭证。

第一版不要求实现账号密码登录。

二维码登录可以作为后续扩展功能。

### 3.2 直播间管理

#### FR-004：添加直播间

用户可以通过以下方式添加直播间：

- 输入直播间 ID
- 粘贴 B 站直播间链接

应用需要解析并验证直播间信息。

直播间信息至少包含：

- 直播间 ID
- 直播间标题
- 主播名称
- 用户自定义备注

其中，直播间 ID 为必要字段。

对于 API 返回的完整信息，可以根据实际情况展示。

#### FR-005：直播间信息展示

直播间列表需要展示：

- 主播名称或直播间备注
- 直播间 ID
- 直播间标题
- 当前关联的任务数量

如果接口支持，还可以展示当前直播状态。

直播状态属于辅助信息，不应该成为整个任务调度模块的强依赖。

首次添加直播间时的解析与必要校验属于 P0；对已保存直播间信息的定期或后台自动刷新属于 P1。

#### FR-006：直播间管理

用户可以：

1. 添加直播间。
2. 编辑直播间备注。
3. 删除直播间。
4. 查看直播间关联任务。
5. 在浏览器中打开直播间。

删除直播间时，需要处理关联任务。

第一版可以采用二次确认后级联删除的方式，但必须明确告知用户影响范围。

---

### 3.3 弹幕任务管理

#### FR-007：创建任务

用户可以创建独立的弹幕任务。

每个任务至少具有以下属性：

| 属性 | 说明 |
|------|------|
| ID | 任务唯一标识 |
| 名称 | 用户自定义任务名称 |
| 直播间 | 目标直播间 |
| 任务类型 | 单次发送或循环发送 |
| 弹幕内容 | 一条或多条消息 |
| 执行计划 | 任务触发规则 |
| 启用状态 | 是否允许自动执行 |
| 运行状态 | 当前执行情况 |
| 创建时间 | 任务创建时间 |
| 修改时间 | 最近修改时间 |

不同任务之间应保持独立。

修改某个任务不应影响其他任务。

#### FR-008：任务类型

第一版支持两种任务类型。

**类型 A：单次发送**

任务触发后发送一条指定弹幕。

发送完成后，本次执行结束。

**类型 B：循环发送**

任务触发后，按照配置的顺序发送多条弹幕。

支持：

- 单条内容循环发送
- 多条内容按顺序循环发送
- 固定发送间隔
- 最大发送次数
- 最大运行时长

循环任务必须设置明确的停止条件。

不提供默认无限循环发送模式。

#### FR-009：弹幕内容编辑

用户可以添加、删除、编辑和排序弹幕内容。

要求：

1. 支持多条弹幕。
2. 支持调整发送顺序。
3. 支持预览发送队列。
4. 自动过滤空内容。
5. 检查弹幕长度及非法内容格式。
6. 根据 B 站接口限制进行输入校验。

对于超出限制的弹幕，不能静默截断。

应提示用户修改内容。

#### FR-010：发送间隔

循环任务支持设置相邻两条弹幕之间的发送间隔。

要求：

1. 支持以秒为单位配置。
2. 提供合理的默认值。
3. 对最短间隔进行限制。
4. 尊重 B 站接口的发送频率限制。
5. 当接口返回频率限制时，停止或暂停发送。
6. 不提供绕过平台频率限制的功能。

第一版默认发送间隔可以设置为 15 秒。

实际允许的最短间隔应结合接口行为和平台规则确定。

#### FR-011：停止条件

循环任务至少支持以下停止条件：

- 达到指定发送次数
- 达到指定运行时长
- 用户手动停止
- 发生需要终止的错误

用户应能够配置发送次数或运行时长。

若两种停止条件同时存在，则任一条件满足即停止任务。

停止时需要取消尚未执行的发送操作。

已经完成的 HTTP 请求无法撤回。

#### FR-012：任务启用和禁用

用户可以启用或禁用任务。

启用任务：

允许任务在未来计划时间自动执行。

禁用任务：

阻止任务在后续计划时间自动启动。

禁用一个正在运行的任务时，应用应明确提示是否同时停止当前执行。

### 3.4 定时调度

#### FR-013：定时任务类型

第一版支持以下调度方式：

**一次性任务**

在指定日期和时间执行一次。

例如：

2026-10-15 22:00

**每日任务**

每天在指定时间执行。

例如：

每天 22:00

**每周任务**

在指定星期执行。

例如：

每周一、三、五的 22:00。

第一版不要求支持完整 Cron 表达式。

#### FR-014：时区支持

每个任务需要有明确的时区定义。

要求：

1. 默认使用 Asia/Shanghai。
2. 允许用户修改任务时区。
3. 任务执行时间按照指定时区计算。
4. 操作系统时区改变时，不应改变已有任务的预期执行时间。
5. 正确处理夏令时和跨日期场景。

调度计算必须由 Go 后端完成。

前端仅负责配置和展示。

#### FR-015：任务自动执行

当满足以下条件时，应用自动执行任务：

1. 应用正在运行。
2. 任务处于启用状态。
3. 当前时间到达计划执行时间。
4. 任务不存在执行冲突。
5. 当前账号凭证满足发送要求。

任务执行不依赖主窗口是否可见。

不要求用户保持 B 站直播页面打开。

#### FR-016：下次执行时间

每个定时任务需要显示：

- 最近一次执行时间
- 最近一次执行结果
- 下一次计划执行时间

禁用任务不显示有效的下一次执行时间。

一次性任务完成后应显示已完成状态。

#### FR-017：避免重复执行

应用必须避免因以下情况导致任务重复启动：

- 短时间重复触发调度
- 用户切换系统时间
- 电脑睡眠后恢复
- 应用窗口重复打开
- 调度器重新初始化
- 应用重启

同一个任务的同一个计划执行实例，只允许自动启动一次。

需要持久化必要的执行标识和调度记录。

手动点击“立即执行”应视为独立执行，不影响既定的下一次计划时间。

#### FR-018：错过执行时间

需要明确处理任务错过计划时间的情况。

例如：

计划时间：22:00

实际情况：

电脑在 21:50 进入睡眠，23:00 才恢复运行。

第一版采用以下规则：

1. 默认不补发错过的任务。
2. 恢复运行后重新计算下一次计划时间。
3. 已错过的执行记录标记为“已错过”。
4. 不因为恢复运行而一次性补发多条历史弹幕。
5. 不要求应用主动唤醒电脑。

一次性任务错过执行时间后，应标记为“已错过”，不自动改期。

#### FR-019：任务冲突处理

需要考虑多个任务同时触发的情况。

要求：

1. 不同任务可以在同一时间处于待执行状态。
2. 同一个任务不能同时产生多个自动执行实例。
3. 实际 HTTP 发送需要进行统一协调。
4. 遵守账号级别的请求频率限制。
5. 当多个任务争用发送能力时，按调度触发顺序排队。
6. 任务排队和实际开始时间应能够在执行记录中体现。

不同直播间的任务也应共享同一账号的发送频率控制。

### 3.5 弹幕发送

#### FR-020：直接调用 B 站接口

应用通过 Go HTTP 客户端直接与 B 站直播弹幕接口通信。

不依赖：

- 浏览器自动化
- 油猴脚本
- Selenium
- Playwright
- BLSPAM
- B 站直播间网页

第一版采用社区已知的直播弹幕接口实现发送。

参考接口：

POST https://api.live.bilibili.com/msg/send

接口参数及认证方式以实际可用的接口规范为准。

由于该接口不是承诺长期稳定的公开第三方服务，需要考虑未来的接口变更。

#### FR-021：发送结果处理

每次发送至少需要识别：

- 发送成功
- 网络连接失败
- 请求超时
- 登录凭证无效
- 发送频率限制
- 接口拒绝
- 参数错误
- 未知错误

不能仅凭 HTTP 状态码 200 判断发送成功。

应进一步检查接口返回的业务状态。

对于接口返回的成功状态，只能认定服务端已接受发送请求，不保证弹幕一定在直播间对所有观众可见。

#### FR-022：发送超时与重试

HTTP 请求需要设置合理的超时时间。

重试原则：

1. 不进行无限重试。
2. 登录失效时不自动重试。
3. 频率限制时遵守服务端限制。
4. 对明确未发送的临时失败，可以进行有限重试。
5. 对发送结果不确定的请求，默认不自动重试，避免重复弹幕。
6. 所有重试行为必须记录。

#### FR-023：立即发送测试

用户可以在界面中执行一次弹幕发送测试。

要求：

1. 选择目标直播间。
2. 输入测试弹幕。
3. 点击发送。
4. 展示发送结果。
5. 失败时显示明确原因。

测试功能必须执行真实的发送请求，不能只检查网络是否连通。

测试发送需要经过与普通任务相同的发送频率限制。

---

### 3.6 任务运行控制

#### FR-024：手动执行任务

每个任务提供“立即执行”操作。

对于单次发送任务：

立即发送对应弹幕。

对于循环发送任务：

按照任务中保存的发送规则启动一次完整执行。

手动执行不得修改任务原有的定时计划。

#### FR-025：停止任务

运行中的任务必须能够被用户主动停止。

停止操作需要：

1. 立即取消后续待发送消息。
2. 取消可取消的网络请求。
3. 更新任务运行状态。
4. 记录停止时间和原因。

#### FR-026：任务执行状态

任务执行实例至少具有以下状态：

- 等待执行
- 排队中
- 正在运行
- 已完成
- 已停止
- 已失败
- 已错过

任务的“启用状态”和“执行状态”必须分开管理。

例如：

一个每日任务可以处于“已启用”，但当前没有正在运行的执行实例。

## 4. 桌面应用能力

### 4.1 后台运行

#### FR-027：关闭窗口时保持运行

应用需要支持关闭主窗口后继续执行后台任务。

要求：

1. 后台调度由 Go 进程负责。
2. 隐藏窗口不得停止正在运行的任务。
3. 再次打开主窗口时可以恢复任务状态。
4. 用户能够明确区分隐藏窗口与退出应用。

关闭按钮行为应提供配置选项。

默认优先采用“隐藏到后台”。

但当系统无法提供可用的恢复入口时，不应把窗口隐藏成用户无法找回的状态。

系统托盘属于 P1；即使未接入托盘，P0 的后台运行也必须提供可靠的主窗口恢复方式。

### 4.2 系统托盘

#### FR-028：托盘菜单

系统托盘属于 P1，应用应尽可能提供该功能。

托盘菜单至少包括：

- 打开主窗口
- 查看运行状态
- 暂停自动调度
- 恢复自动调度
- 退出应用

Linux 平台需要考虑不同桌面环境对托盘图标的支持差异。

在无法显示托盘图标的桌面环境中，需要提供可靠的备用操作方式。

### 4.3 开机自启动

#### FR-029：开机自启动设置

开机自启动属于 P1。实现后，用户能够选择是否在登录操作系统后自动启动应用。

要求：

1. 默认关闭。
2. 支持在设置中启用或禁用。
3. 启用后在用户登录桌面会话时启动。
4. 支持启动后不显示主窗口。
5. Windows 与 Linux 均需要支持。
6. 关闭自启动时正确清理此前创建的启动项。

开机自启动不等于系统未登录时执行。

第一版不要求在无图形用户会话的情况下运行。

### 4.4 应用退出

#### FR-030：退出确认

当存在已启用的定时任务或正在运行的任务时，用户选择退出应用，应提示：

退出后定时任务将停止执行，直到应用再次启动。

退出应用时：

1. 停止调度器。
2. 取消待执行请求。
3. 持久化任务状态。
4. 释放必要的系统资源。

### 4.5 单实例运行

#### FR-031：防止重复启动

同一用户会话中默认只允许运行一个应用实例。

当用户重复启动应用时：

1. 不创建第二个调度器。
2. 不重复启动定时任务。
3. 优先激活已有应用窗口。

## 5. 图形界面需求

### 5.1 总体要求

第一版提供完整的桌面图形界面。

界面应简洁、直观，避免过度复杂的配置操作。

桌面窗口布局遵循以下约束：

- 窗口最小尺寸为 **1080 × 680**（逻辑像素），默认启动尺寸为 **1280 × 760**；启动时不得超出操作系统可用工作区，实际边框及显示缩放由目标平台验证。
- 在不小于最小尺寸的正常桌面窗口中，**所有页面的整体内容区域均不应产生横向或纵向滚动条**。页面标题、主要操作和导航保持可见，剩余空间由页面内容区域自适应分配。
- 内容超过容器可用空间时，允许任务列表、记录列表、设置分组、编辑表单等**明确划定的内容容器独立滚动**；不能通过直接裁切来掩盖不可访问的功能或信息。对过长文本采用合理截断、换行或可查看详情的方式处理。
- 总览页的「最近执行」可按窗口高度展示 **2～5 条**记录，其余通过「全部记录」进入执行记录页；即将执行及异常内容超出时，可在对应卡片内部滚动。
- 原型至少使用 1080 × 680、1280 × 720、1366 × 768、1728 × 864、1920 × 1080 视口进行布局检查，并在 Windows / Linux 的正式窗口验证最小尺寸、系统缩放及内容可访问性。

**列表加载规则：**

- **执行记录**使用页码分页：在当前窗口可用高度内按完整数据行计算每页容量，包含全部匹配结果时不显示分页控件；超出一页时在列表底部固定展示上一页、当前页码、下一页和记录范围，切换页码不滚动整个页面。最后一页不足以铺满内容区时，在末条记录下方显示分割线和结束提示；筛选条件变化后返回第一页；展开单条详情时只允许记录内容区局部滚动。
- **弹幕任务、直播间（卡片和列表视图）**使用游标增量加载：按稳定顺序获取首批数据，滚动至内容区底部时继续加载下一批，必要时提供可点击的“加载更多”入口；有更多数据时不显示页码，全部加载完成且内容较少时继续使用现有分割线与“已全部显示”提示。搜索、筛选或排序条件变化后重置游标和已加载结果，避免重复、遗漏记录。
- **总览页**仅展示有限条摘要，通过“全部任务”“全部记录”进入对应完整页面，不在总览中分页。
- 总览页的「最近执行」表头与数据行滚动区域分离：表头固定可见，滚动条仅出现在数据内容区，不占用表头或外层页面。
- 数据接口沿用 [HTTP API 设计规范](specs/standards/backend/HTTP%20API%20设计规范.md) 中的页码分页（`page`、`pageSize`、`total`、`totalPages`）和游标分页（`cursor`、`limit`、`nextCursor`、`hasMore`）约定。当前原型仅模拟前端列表交互，不代表正式存储查询接口已经实现。

本节只约定界面功能与使用体验，不规定具体技术实现。前端框架、组件库、视觉设计等已在 [技术栈选型](技术栈选型.md) 中确定。当前独立的 [UI 原型](../prototype/README.md) 仅用于探索页面和交互，不代表功能已经在正式应用中实现。

## 6. 数据存储需求

### 6.1 本地存储

第一版不需要云端数据库。

所有任务配置、执行记录和应用设置保存在本地。

必须支持应用重启后的数据恢复。

需要存储：

1. 直播间列表。
2. 任务定义。
3. 弹幕内容。
4. 调度规则。
5. 任务启用状态。
6. 执行记录。
7. 最近一次调度信息。
8. 应用设置。

### 6.2 凭证隔离

普通应用数据与账号凭证需要分别管理。

普通配置数据中不得保存：

- SESSDATA 明文
- bili_jct 明文
- 完整 Cookie
- 其他敏感认证信息

### 6.3 数据位置

应用数据应保存在对应操作系统推荐的用户数据目录中。

不得默认保存在：

- 用户桌面
- 应用安装目录
- 当前工作目录
- 随意创建的临时目录

应提供“打开数据目录”功能，方便用户检查文件。

### 6.4 数据一致性

保存任务配置时应确保数据完整。

要求：

1. 不因应用异常退出而损坏全部配置。
2. 删除任务时同步处理关联数据。
3. 修改任务时保留唯一标识。
4. 任务执行记录应能正确关联原任务。
5. 读取损坏配置时应给出错误提示，而不是静默覆盖全部数据。

### 6.5 日志保留

第一版默认保留最近 30 天的执行记录。

手动清理历史记录属于 P1；默认保留期限和自动清理规则不因此取消。

应区分：

- 任务执行记录
- 应用诊断日志

诊断日志不得包含完整认证凭证。

应用诊断日志在 P0 默认开启，独立于 SQLite 执行历史，应用启动和数据库初始化失败也应尽可能留下诊断信息；正式桌面发行版不能依赖终端输出。使用结构化本地日志，默认 `info`，初始建议单文件不超过 10 MiB、最多 5 个文件（含当前文件）、最多保留 14 天；应按大小和时间清理，避免长期运行无限增长。日志写入故障不得阻断核心业务，但应提供可观察的降级提示。

日志只记录必要的时间、组件、事件、非敏感标识、结果类别及耗时；不得记录 Cookie、Keyring 内容、弹幕正文、HTTP 请求体、原始上游响应或可能含敏感信息的底层错误。用户可主动导出经过敏感信息检查的诊断包，包含必要版本 / 平台信息及限定范围的日志，不默认包含数据库或执行历史，也不自动上传。诊断日志查看与手动清理仍属于 P1，30 天执行历史保留规则不变。

## 7. 调度与运行可靠性

### 7.1 调度器职责

调度器需要负责：

- 读取启用任务
- 计算下一次执行时间
- 按时触发执行
- 管理任务排队
- 防止重复启动
- 处理任务取消
- 维护执行状态
- 记录执行结果

调度器必须独立于前端界面运行。

前端关闭、刷新或重建时，不得导致后端任务重复执行。

### 7.2 任务执行器职责

任务执行器负责：

- 读取任务配置
- 生成发送队列
- 控制发送间隔
- 调用弹幕发送服务
- 处理取消请求
- 检查停止条件
- 汇总执行结果

调度器不应直接包含弹幕 HTTP 请求的具体实现。

### 7.3 状态恢复

应用启动时需要：

1. 加载持久化任务。
2. 检查未正常结束的执行记录。
3. 将上次异常中断的执行标记为中断。
4. 重新计算所有启用任务的下一次执行时间。
5. 恢复正常调度。

默认不恢复上次未完成的循环发送进度。

不补发应用关闭期间错过的弹幕。

### 7.4 系统睡眠

当电脑睡眠时，应用无法保证按时运行。

恢复后应：

1. 重新读取当前时间。
2. 重新计算任务计划。
3. 标记错过的任务。
4. 避免重复执行。
5. 继续等待未来任务。

第一版不要求阻止系统睡眠，也不要求自动唤醒电脑。

### 7.5 网络异常

发送期间如果网络断开：

1. 显示网络错误。
2. 按既定重试规则处理。
3. 避免高频重复请求。
4. 达到失败条件后终止本次执行。
5. 不影响其他任务配置。

## 8. 非功能性需求

### NFR-001：跨平台

第一版正式支持：

- Windows 10 / 11，x86_64
- Linux，x86_64

Linux 优先验证：

- Fedora GNOME
- 常见 X11 / Wayland 桌面会话

各平台应尽量保证功能一致。

系统托盘、开机自启动和窗口行为允许使用平台特定实现。

### NFR-002：资源占用

应用在后台空闲时应保持低资源占用。

要求：

- 不使用高频轮询检查时间。
- 不持续刷新隐藏的前端界面。
- 不创建不必要的后台线程。
- 不在没有发送任务时持续请求 B 站接口。

### NFR-003：响应性能

目标：

1. 普通界面操作响应流畅。
2. 任务保存后立即更新列表。
3. 调度计算不阻塞主界面。
4. 网络请求不阻塞主界面。
5. 普通情况下尽量将计划执行误差控制在 1 秒以内。

执行精度不保证为硬实时。

实际网络发送时间受到系统调度和网络延迟影响。

### NFR-004：错误处理

所有可能失败的关键操作必须具有明确反馈。

不允许出现：

- 静默发送失败
- 任务卡在运行中
- 登录失效后持续重试
- 发生错误后无限发送
- 任务失败但显示成功

### NFR-005：可维护性

核心业务逻辑使用 Go 实现。

模块之间应保持清晰的职责边界。

特别是以下模块应相互解耦：

- 任务管理
- 调度器
- 任务执行器
- B 站 API 客户端
- 账号凭证管理
- 持久化存储
- 桌面应用生命周期

前端只通过明确的应用服务接口访问后端功能。

### NFR-006：安全性

要求：

1. 不向第三方服务上传登录凭证。
2. 不在日志中保存完整 Cookie。
3. 不在普通配置中明文保存敏感信息。
4. 对输入内容进行必要校验。
5. 网络请求使用 HTTPS。
6. 对接口异常返回进行安全处理。
7. 不实现验证码绕过、风控规避或平台限制绕过。
8. 自动发送功能应遵守平台相关规则。

## 10. 典型业务流程

### 10.1 首次使用

1. 用户启动应用。
2. 应用初始化本地数据。
3. 检查是否已配置 B 站账号。
4. 如果未配置，提示用户设置登录凭证。
5. 用户输入并保存凭证。
6. 应用验证账号状态。
7. 验证成功后进入正常使用状态。

### 10.2 创建定时任务

1. 用户进入任务管理页面。
2. 点击新建任务。
3. 输入任务名称。
4. 选择目标直播间。
5. 选择任务类型。
6. 输入弹幕内容。
7. 配置发送间隔及停止条件。
8. 配置定时规则。
9. 保存任务。
10. 应用计算下一次执行时间。
11. 用户启用任务。
12. 调度器注册任务。

### 10.3 自动执行任务

1. 调度器发现任务到达计划时间。
2. 检查任务是否启用。
3. 检查本次执行是否已经触发。
4. 创建执行记录。
5. 任务进入执行队列。
6. 任务执行器读取任务配置。
7. 检查账号凭证状态。
8. 按规则调用弹幕接口。
9. 记录每次发送结果。
10. 达到停止条件后结束本次执行。
11. 保存最终执行结果。
12. 计算下一次计划执行时间。

### 10.4 用户手动停止任务

1. 用户打开任务列表。
2. 找到正在运行的任务。
3. 点击停止。
4. 应用取消后续发送操作。
5. 任务执行器结束。
6. 任务状态更新为已停止。
7. 写入执行记录。

### 10.5 应用异常退出后重新启动

1. 应用重新启动。
2. 加载持久化数据。
3. 检查上次执行状态。
4. 将异常中断的任务执行标记为中断。
5. 不自动补发已经错过的弹幕。
6. 重新计算未来执行时间。
7. 恢复自动调度。

## 11. 第一版验收标准

### AC-001：账号配置

给定用户提供有效的 B 站登录凭证，

当用户保存凭证并执行验证时，

应用应能正确显示登录状态。

无效凭证应显示明确错误。

### AC-002：单条弹幕发送

给定用户已登录且目标直播间有效，

当用户点击立即发送时，

应用应调用 B 站接口发送指定弹幕，并显示实际结果。

### AC-003：多条循环发送

给定用户配置三条弹幕、15 秒间隔和明确的停止条件，

当用户执行任务时，

应用应按照规定顺序发送消息，并在达到停止条件后结束。

### AC-004：每日定时任务

给定用户创建一个每天 22:00 执行的任务，

当应用正常运行且时间到达 22:00 时，

应用应自动触发任务，不需要用户打开直播间网页。

### AC-005：窗口隐藏

给定应用已经启用定时任务，

当用户隐藏主窗口时，

调度器应继续正常运行。

### AC-006：系统睡眠

给定任务计划在 22:00 执行，

当系统从 21:50 睡眠到 23:00 时，

任务不应在恢复后自动补发。

### AC-007：防止重复执行

给定某任务已经完成当天的自动执行，

当系统时间变化或调度器重新初始化时，

应用不得自动再次执行相同的计划实例。

### AC-008：登录失效

给定账号凭证已经失效，

当任务尝试发送弹幕时，

应用应停止发送并记录认证错误。

### AC-009：任务持久化

给定用户已经创建多个任务，

当应用退出并重新启动后，

任务配置、启用状态和历史记录应正确恢复。

### AC-010：跨平台

应用应分别在 Windows 和 Linux 上完成以下测试：

- 启动应用
- 配置账号
- 添加直播间
- 创建任务
- 定时发送
- 循环发送
- 手动停止
- 后台运行
- 退出与重新启动

核心业务结果需要保持一致。

### AC-011：并发与频率限制

给定两个任务在同一时间触发，

当两者使用同一个账号发送弹幕时，

应用应正确协调发送顺序，并避免违反统一的频率限制。

### AC-012：异常处理

给定发送时发生网络超时、接口错误或认证失效，

应用应正确结束或暂停对应执行，

并在执行记录中保留可理解的错误信息。

## 12. 开发优先级

P0 是首版最低交付范围，必须满足相应功能需求和第 11 节验收标准；P1 是可在 P0 完成后补充的增强项，不应被前文界面需求中的“支持”或“包含”表述提升为 P0。两者共享的基础行为（如登录失效后的错误反馈）仍属于 P0。

### P0：核心功能，第一版必须完成

- Wails 3 桌面应用基础框架
- B 站单账号凭证管理、账号状态验证及失效反馈
- 直播间添加、必要信息校验与管理
- 单条弹幕发送与真实测试发送
- 多条弹幕循环发送
- 发送间隔及停止条件
- 一次性 / 每日 / 每周任务
- 后端定时调度器
- 任务启用、禁用及停止
- 任务执行记录及单次执行详情（不要求多条件筛选）
- 本地数据持久化
- 后台运行及可靠的窗口恢复入口（不依赖必须有系统托盘）
- 任务去重、单实例及异常恢复
- 核心操作失败时的明确错误反馈
- Windows / Linux 基础兼容性

### P1：第一版建议完成

- 系统托盘
- 开机自启动
- 启动后隐藏窗口
- 执行记录筛选
- 手动历史清理、诊断日志查看与清理
- 登录失效的额外提醒方式（如系统通知）
- 直播间信息自动刷新（首次添加时的必要校验属于 P0）
- 任务编辑过程中的执行预览
- 应用语言切换
- 错误提示的操作建议与文案优化

P1 功能不应阻塞核心发送与调度能力的实现。

但作为长期常驻的桌面应用，系统托盘和开机自启动应尽量在首个正式发布版本中完成。

## 14. 技术边界与约束

### 14.1 已确定的技术约束

- 使用 Go 实现后端业务逻辑。
- 使用 Wails 3 构建桌面应用。
- 支持 Windows 和 Linux。
- 直接通过 HTTP 接口发送 B 站直播弹幕。
- 不依赖浏览器页面。
- 调度逻辑运行在 Go 后端。
- 本地保存任务和执行记录。
- 不需要外部服务器。

### 14.2 技术方案的决策状态

前端框架、组件库、设计系统、状态管理、Wails 前后端通信、SQLite、Go 代码组织和日志方案已经在 [技术栈选型](技术栈选型.md) 中明确；这些是**目标方案**，不代表仓库已完成接入。数据库结构另见 [SQLite Schema 与 Migration 设计](SQLite%20Schema%20与%20Migration%20设计.md)。

发布和打包细节、CI/CD 方案，以及未被现有技术设计覆盖的实现细节，仍按开发进度确定。需求文档不对这些尚未定案的技术细节作强制规定。

### 14.3 外部服务约束

本项目依赖 B 站直播弹幕接口。

需接受以下限制：

1. 接口可能发生变更。
2. 登录凭证可能失效。
3. 平台可能限制发送频率。
4. 某些弹幕可能受到服务端审核或过滤。
5. 网络环境可能导致请求失败。
6. 无法保证平台永久允许第三方客户端发送弹幕。

应用必须能够识别和合理处理这些情况。

## 15. 第一版交付标准

第一版完成后，用户应能够通过图形界面完成如下完整操作：

1. 安装并启动应用。
2. 配置 B 站账号。
3. 添加目标直播间。
4. 创建弹幕发送任务。
5. 设置每天晚上 22:00 执行。
6. 配置一条或多条弹幕。
7. 设置循环间隔和停止条件。
8. 启用任务。
9. 将应用保持在后台运行。
10. 到达计划时间后自动发送弹幕。
11. 查看发送结果和执行记录。
12. 随时禁用、编辑或删除任务。

整个过程无需打开 B 站直播间网页，也无需操作外部独轮车脚本。

### 最终验收目标

在 Windows 和 Linux 上，用户均可以通过一款 Wails 3 桌面应用，稳定管理 B 站直播弹幕定时任务，实现自动发送、循环发送、后台运行和执行记录查询。

第一版应优先保证：

**定时可靠、发送可控、状态准确、凭证安全、跨平台一致。**

不以功能数量作为第一版的主要完成标准。
